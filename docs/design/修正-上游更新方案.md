## 四、✅ 真实缺陷：QQ 表情 ID 整数溢出

这是本轮核验中**唯一确认需要修复的 Phase 1 条目**。

### 4.1 问题

```js
// lib/qq-im/face.js:89
const FACE_MARK = /\[face:\s*(\d+)\s*\]/gi      // ← 不限位数

// lib/qq-im/face.js:104-108
export function describeFace(id) {
  let key = Number(id)
  if (!Number.isFinite(key)) return '[表情]'
  key |= 0                                        // ← 静默回绕，无范围校验
  return FACE_NAMES[key] ?? `[表情${key}]`
}
```

`key |= 0` 把超范围值**回绕**成另一个合法 id，而不是拒绝。实测复现：

```
14               -> key=14           -> 微笑
4294967310       -> key=14           -> 微笑        ← 撞上真实表情（别名）
2147483662       -> key=-2147483634  -> [表情-2147483634]
999999999999     -> key=-727379969   -> [表情-727379969]
```

### 4.2 影响与严重度

- **严重度：中低**。不崩溃（`?? ` 兜底保证有输出），后果是**表情标签误导**。
- 触发条件：入站文本含畸形/超大 `[face:N]`（恶意构造或上游 SDK 异常）。
- 附带影响：`describeFace` 的负数输出会进入注入上下文，模型看到 `[表情-2147483634]` 属噪声。

### 4.3 修复方案

```js
// 方案 A（推荐）：收紧匹配 + 范围校验
const FACE_MARK = /\[face:\s*(\d{1,3})\s*\]/gi
const MAX_FACE_ID = 160   // FACE_NAMES 覆盖 0–160

export function describeFace(id) {
  const key = Number(id)
  if (!Number.isFinite(key) || !Number.isInteger(key) || key < 0 || key > MAX_FACE_ID) {
    return '[表情]'
  }
  return FACE_NAMES[key] ?? `[表情${key}]`
}
```

**要点**：
1. `\d{1,3}` 从入口就挡住长数字串；
2. 显式范围校验替代 `|= 0` 的回绕语义；
3. 超范围统一回退 `[表情]`（而非输出负数），避免噪声进上下文。

> **一个必须注意的行为差异**（已实测）：收紧正则为 `\d{1,3}` 后，
> `[face:4294967310]` 这类超长标记会**完全不被匹配**，
> 于是**原样保留**在文本里（输出 `[face:4294967310]`），而不是变成 `[表情]`。
>
> 这比「撞上真实表情」好，但**仍会把原始标记暴露给模型**。
> 若要彻底清理，应**同时保留一个宽匹配的兜底**：
>
> ```js
> // 先做窄匹配（正常路径）
> text = text.replace(/\[face:\s*(\d{1,3})\s*\]/gi, (_m, id) => `[${describeFace(id)}]`)
> // 再做兜底：任何残留的 [face:...] 一律清理
> text = text.replace(/\[face:[^\]]*\]/gi, '[表情]')
> ```
>
> 实施时请据此设计测试用例，明确期望到底是「原样保留」还是「清理为 [表情]」。

**测试**：新增 `test/qq-im/face-overflow.test.mjs`，钉住
`4294967310`、`2147483662`、`999999999999` 均返回 `[表情]` 而非撞上 `微笑`。
并确认 `humanizeFaces` 正常路径（`[face:14]` → `[微笑]`）不回归。

> **注意**：`restoreFaces` / `protectFaces`（`face.js:156,172`）会原样透传
> 匹配到的 `[face:N]`。修 `FACE_MARK` 后需回归 `test/qq-im/face.test.mjs`
> 与 `test/qq-im/inbound.test.mjs`，确认回显路径行为符合预期。

### 5.1 认知证据系统（knowledge-evidence）— 最高 ROI

**上游实现**：`src/script/knowledge-evidence.ts`（108 行）

**核心机制**（已逐行核对）：

```ts
mode: 'observed' | 'reported' | 'belief' | 'proposal' | 'conditional' | 'confirmed' | 'unclassified'
clauses: Array<{ role: 'observation'|'interpretation'|'proposal'|'condition'|'confirmation';
                 sourceEntryId: number; quote: string }>
```

三条硬规则：

1. **逐字校验**（`:23-24`）：`quote` 必须**逐字包含于** `entry.content`，且
   `quote.length <= 800`，否则该 clause **直接丢弃**。
2. **confirmed 需双向交换**（`:32-41`）：必须存在一个 `proposal` 和一个
   `confirmation`，分别来自 `user-message` 与 `character-message`（**kind 不同**）、
   **同一 participantId**、且 `confirmation.id > proposal.id`。
   不满足则降级为 `conditional` 或 `unclassified`。
3. **主观解读降级**（`:43`）：`mode === 'observed'` 但含 `interpretation` clause
   → 自动降为 `belief`。

另有：`authority` 字段（`:66`）——`belief` 标 `attributed-belief`，其余标 `derived-record`。

**DSH 适配方案**：

| 步骤 | 内容 | 难点 |
|------|------|------|
| ① Schema | `interlude_memory` 新增 `knowledge` 字段（`mode`, `clauses[]`） | 低 |
| ② 存储 | `state.js` 的 `addFact` 增加 `knowledge` 承载 | 低 |
| ③ **校验** | **需要「近期续写文本 + 逐字包含」的可回溯来源** | **高** |
| ④ 排序 | `rankFacts` 中 `confirmed` 权重高于 `belief` | 低 |
| ⑤ 注入 | `render.js` 幕间块注入认知写作指引 | 低 |

> **③ 是真正的障碍**。上游 `clauses[].sourceEntryId` 指向 SQLite 的
> `interlude_script_entry` 表，`entry.content` 是该条剧本原文。
> **DSH 没有这张表**——续写文本存在 Agent 会话日志中，不是独立可索引字段。
>
> **建议适配路径**：不追求「指向历史 entry id」，改为**当轮校验**——
> 即 `interlude_memory` 调用时，把该回合的续写正文（或其摘要）作为校验语料，
> 要求 `quote` 逐字出现在其中。**证据随事实一同落盘**（存 quote + 校验时间戳），
> 而不是存一个无法解析的 entry id。这样保持「逐字可查」的约束，
> 又不需要重建剧本表。**此方案需先做原型验证再全量实施。**

   上游 `development.ts:83` 的门控针对的是**候选提案**（`StatePatchProposal`），
   本地没有这层结构。

2. **`evidence` 字段已经在计数**（`state.js:582`），但目前**无阈值判断**。

**且**：仓库既有文档 `源码直读-上游复用改进方案.md` 的 §8.2 与 **遗留待确认项**
明确记录过这一点：

> overlay 是否需要像上游那样加**证据门控**（`minEvidence` / `minDays` / 冷却）？
> 本轮只补了接线，判据未加 —— **建议先观察实际写入频率再定**，
> 拍脑袋的阈值容易误伤。

**修正建议**：**暂不加门控**。先观察实际写入频率，再决定阈值。
若确实需要，最小改动是给 `upsertOverlay` 增加 `evidence >= N` 才注入提示词的判断，

## 八、核验方法说明（供后续复用）

原方案出错的**根本原因**：用 changelog 标题和版本号推断「上游有什么」，
再假设「本地没有什么」，**从未做源码级比对**。

仓库既有文档 `源码直读-上游复用改进方案.md` 的 §九 已记录过同类教训：

> 1. **grep 字面量会漏掉正则变量名。** 核实「有没有某能力」时，
>    应同时搜**用法**与**定义**（变量名、常量名）。
> 2. **接线要接两端，还要核对闸门。**

**本轮新增的第三条教训**：

> 3. **不要用版本号/changelog 推断代码差异。**
>    changelog 标题 ≠ 已发布版本；`v0.1.5-beta10` 这类内部构建号
>    会让人误以为存在大量增量改动。**权威依据是 `git diff <基线> <目标>`**。
>    本轮据此发现：原方案声称需要同步的四个模块，上游**一行未改**。
