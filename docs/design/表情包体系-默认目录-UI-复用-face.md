# 表情包体系：默认目录、UI、用户表情复用、QQ 原生 face

> 承接《接通-图片通路-表情包.md》。那一轮接通了发图的基础通路；
> 这一轮补齐「怎么让模型用得顺手」与「QQ 原生表情」两块。

## 四件事

| 需求 | 做法 |
| --- | --- |
| 没给路径就用默认路径 | 默认 `~/.dsh/media/stickers/`，工具新增 `name` 参数按名字找 |
| UI 加路径设置（同工作区选择方式） | 复用 `pickDirectory` + `fs/list` 回退，与工作区选择器同一套代码 |
| 用户发过的表情存下来复用 | 入站图片自动落盘、内容 hash 去重、按发送者分目录 |
| QQ 原生 face 适配 | `[face:14]` ↔ `[微笑]` 双向翻译，并防止被清洗管线吃掉 |

## 默认路径为什么选 `~/.dsh/media/stickers/`

表情包是**跨项目**的资产。跟着 workspace 走的表现是「在 A 项目能发表情、
切到 B 项目就找不到了」——而且排查时很难想到是路径基准变了。

所以：
- 放在 `DSH_HOME` 下，与其它持久数据同级；
- 配置里留空即用默认目录（**不把默认值固化进配置**，否则以后改默认值对老用户不生效）；
- 相对路径按用户主目录解析，不按进程 cwd。

目录结构：

```
~/.dsh/media/stickers/
  index.json                     # 元数据清单（名字/来源/时间）
  mine/                          # 角色自己的图（用户手工丢进来即可用）
    开心.png
  from-A1B2C3D4/                 # 用户发来的，按发送者分
    d0d617a32620e2dc.png
```

按发送者分目录不是洁癖：不同人的表情包语域不同，
「用 A 的表情回 B」在真人聊天里是件很奇怪的事。分开存，模型才有得选。

### 清单与磁盘的关系

`index.json` 只存**元数据**，真图片始终以磁盘为准。用户往目录里手工丢图
（不写清单）也能被列出——这个用法必须能用，否则「把表情包放进目录」
这条最自然的路径就走不通了。

## 模型怎么用

```js
interlude_stickers()                              // 先看看有什么
interlude_send_image({ name: "开心" })             // 按名字发（推荐）
interlude_send_image({ file_path: "D:/a.png" })    // 也可以给路径
interlude_send_image({ url: "https://…" })         // 或者网图
```

`name` 优先是刻意的：要求模型记住 `D:/pics/xx.png` 这种绝对路径不现实，
而「从库里挑一个叫开心的」是它能稳定做对的事。

**找不到时不猜**。匹配只看精确名 / 不区分大小写 / 唯一前缀；
多个候选一律返回 undefined，并把库里现有的名字列进错误信息——
发错表情包是无法撤回的社交事故，宁可报错。

`file_path` 只给文件名（无目录分隔符）时会到表情库找同名文件：
模型常把 `file_path` 当「文件名」用，宽容一点比报错有用。

## 用户表情自动收割

QQ 入站图片给的是 `attachments[].url`，**会过期**（腾讯 CDN 临时地址）。
所以「用户发过的表情可复用」这件事不落盘就是做不到的——存 URL 等于存了个快失效的引用。

实现要点：
- **按内容 sha256 去重**，不按 URL。QQ 的 URL 每条都不同，同一张图发两次会得到两个 URL，只有内容 hash 认得出是同一张；
- 落盘用「先写 `.tmp` 再 rename」，中途失败不会留下半张图被当有效表情包；
- 只收 `image/*`（按 content_type 判，不信扩展名），单张上限 10MB；
- **永不抛错、不 await**：收割是旁路，绝不能拖慢或挡住消息注入模型。

## QQ 原生 face

`[face:14]` 是**文本标记**，不是媒体消息——不需要任何新通路，
只要保证它不被当噪声删掉。

两个方向共用一份 id 表（`face.js` 的 `FACE_NAMES`），
避免「收进来是微笑、发出去变成别的脸」。

### 踩到的坑：清洗管线会吃掉 face

这是本轮最容易坏的一环，已用测试钉死：

```
cleanImText('[face:14]')              → ''          ❌ 被当「整行方括号旁白」删掉
splitOutboundText('[face:14]')        → []          ❌ 分条同样过 clean
```

后果很具体：模型**只发一个表情**时，那一行就是 `[face:14]`，
会被删得干干净净，变成「这一轮什么都没说」。

更反直觉的是修法。直觉会写成「先清洗再分条」，但**没用**：

```
cleanKeepingFaces('[face:14]')  → '[face:14]'   ✅ 保护住了
splitImText('[face:14]')        → []            ❌ 又被清掉
```

因为 `splitImText` **内部自己会再清洗一次**。保护必须包在**分条外面**：
先把 face 换成占位符，整段交给分条（内部怎么清洗都伤不到占位符），
分完再逐条还原。见 `splitKeepingFaces`。

保护不能顺手放行真旁白——`（她犹豫了一下）` 仍然要被删掉，有测试盯着。

id 表只收常用的一批（约 160 个）。全表 200+ 且大量是历史遗留与游戏联动，
收全了既没意义又难维护；表里没有的 id 走 `[表情N]` 兜底，不丢信息。
重名（如 0 和 14 都叫「微笑」）取**最小 id**，这是 QQ 的经典版，兼容性最好。

## UI

「表情包目录」选择器与工作区选择器**同一套方式**：优先 `pickDirectory`
（系统目录选择器），不可用时回退自建 `fs/list` 浏览弹窗。
`dirPicker` 用 `'sticker'` 作为 target 标记复用同一套弹窗组件。

新增四个开关（默认全开）与表情库缩略图预览：

- 允许角色发表情包 / 图片（`imagesEnabled`）
- 把对方发来的图片存进表情库（`harvestInbound`）
- QQ 原生表情双向适配（`faceEnabled`）
- 表情包目录（`stickerDir`）

缩略图走 `/api/hds-interlude/sticker-file?i=N`，**按表情库下标取**而不是
接受任意路径——这样请求方无法用它读目录外的文件（有测试验证）。
