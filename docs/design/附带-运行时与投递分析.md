# Reference Runtime Report — hds-interlude (Koishi/TS) vs. dsh-hds-interlude (DSH/JS)

Scope: read-only analysis of the reference's orchestration/runtime layer, focused on
delivery, scheduling, concurrency, persistence, compaction, and failure semantics —
and what of it we have **not** replicated.

Files examined:

| Ref | Lines | Role |
|---|---|---|
| `hds-interlude-master/src/service.ts` | 6877 | story/narrative service: buffering, scheduling, delivery, compaction, write queue |
| `hds-interlude-master/src/database.ts` | 149 | 13 tables |
| `hds-interlude-master/src/time.ts` | 96 | timezone/clock helpers |
| `dsh-hds-interlude/lib/index.js` | 2032 | our scan, `handleProactive`, `handleAutoAdvance`, `inFlight` |
| `dsh-hds-interlude/lib/state.js` | 320 | our per-session JSON state |
| `dsh-hds-interlude/lib/im.js` | 321 | our chunking + `deliverImChunks` |
| `dsh-hds-interlude/lib/capture.js` | 110 | our write-back capture |

Verdict up front: **our delivery is a single best-effort RPC call; the reference's is a
persisted, resumable, per-segment state machine.** That gap, plus the absence of a
serialized write path, is the substance of this report.

## 1. Delivery pipeline

### 1.1 The reference: two distinct lanes

The reference splits delivery into two different mechanisms depending on whether the
text is already decided.

**Lane A — live turn, delivered immediately.** `flushBufferedNarrative` reaches the
narrator, then hands the resulting drafts to `sendOutgoingMessages`:

```ts
// service.ts:2391-2393
if (this.canHandleParticipant(snapshot.participant)) {
  const delivered = await this.sendOutgoingMessages(snapshot.story, result.messages, snapshot.participant, turn.latestSession)
  await this.confirmOutgoingDeliveries(snapshot.story, delivered)
```

**Lane B — background/scheduled, delivered via the intent table.** `sendScheduledMessages`
is used by `sweep()`:

```ts
// service.ts:3981-3985
private async sendScheduledMessages(story: InterludeStory, messages: OutgoingMessageDraft[]) {
  const delivered = await this.sendOutgoingMessages(story, messages)
  await this.confirmOutgoingDeliveries(story, delivered)
  return delivered
}
```

### 1.2 Ordering and partial failure

`sendOutgoingMessages` is a **sequential `for` loop, not `Promise.all`** — order is
guaranteed, and each message is independent. Every failure path is a `continue` that
records a distinct reason string:

```ts
// service.ts:4009-4057 (abridged; all failure branches shown)
for (const message of messages) {
  const target = byId.get(message.participantId)
  if (!target) {
    if (recordFailures) await this.recordOutgoingDeliveryFailure(story, message.participantId, message, 'participant-not-found')
    continue
  }
  if (!this.canHandleParticipant(target)) { ... 'participant-not-allowed'; continue }
  if (shouldCancel?.(target)) { ...; continue }
  try {
    const literalQuoteMessageId = await this.resolveLiteralQuoteMessageId(story.id, target.id, message.content)
    ...
    if (session && current?.id === target.id) { await session.send(outgoingContent); delivered.push(message); continue }
    const bot = this.findBotForParticipant(target)
    if (!bot) { ... 'bot-not-found'; continue }
    await bot.sendMessage(target.channelId, outgoingContent)
    delivered.push(message)
  } catch (error) {
    this.report('warn', story, 'intent-due', '消息投递失败 参与者=%s 错误=%s', target.id, error)
    if (recordFailures) await this.recordOutgoingDeliveryFailure(story, target.id, message, `transport-error: ${String(error)}`)
  }
}
return delivered
```

**Crucial design decision — deliberate non-retry of a possibly-sent message:**

```ts
// service.ts:4062-4065
/** Confirm visible delivery only after the platform accepted the message.
 * Failed attempts become explicit system evidence rather than fictional
 * character speech, and deliberately do not auto-retry to avoid duplicates
 * when an adapter fails after it has already accepted a request. */
```

So: **at-most-once for the main body**, with the failure persisted as a *system* entry,
not as character speech:

```ts
// service.ts:4105-4113
await this.appendEntry(story.id, {
  kind: 'outgoing-delivery-failed', actor: 'system',
  content: `未投递的主角消息（仍未发送，不能视为用户已收到）：${clip(message.content, this.config.runtime.maxMessageCharacters)}`,
  occurredAt: now.toISOString(),
  metadata: { status: 'pending', participantId, reason: clip(reason, 500), ... },
}, now, participantId)
```

Note `status: 'pending'` in the metadata — the failure is *evidence with a state*, and
critically the failed message never enters canon as something the user heard.

For **split segments**, retry IS safe and IS done, because the segment is persisted
before transport:

```ts
// service.ts:2525-2531
if (!delivered.length) {
  if (this.interruptedTypingParticipants.has(participant.id)) continue
  const retryAt = new Date(now.getTime() + 30 * Time.second)
  await this.dbSet('interlude_intent', { id: intent.id }, { notBefore: retryAt, updatedAt: now })
  this.scheduleDueIntentWake(story.id, retryAt)
  continue
}
```

This is the key asymmetry: **retry the text that is durably queued; never retry the
RPC you might have already completed.**

### 1.3 Message splitting: `<sep/>` as a *persisted future event*

Splitting itself is trivial:

```ts
// service.ts:4153-4158
private splitOutgoingMessage(content: string) {
  if (this.config.runtime.splitReplyMessages === false) return [content]
  const separator = this.config.runtime.messageSeparator?.trim() || '<sep/>'
  if (!separator || !content.includes(separator)) return [content]
  return content.split(separator).map(part => part.trim()).filter(Boolean)
}
```

The interesting part is what happens to segments 2..N. They are **not** sent in a loop.
They are each written as an `interlude_intent` row with a computed future `notBefore`,
and a wake timer is armed:

```ts
// service.ts:4084-4097 (inside confirmOutgoingDeliveries, per confirmed message)
let delay = 0
for (const segment of message.laterSegments ?? []) {
  delay += this.typingDelayMilliseconds(segment)
  const sendAt = new Date(now.getTime() + delay)
  await this.appendIntent(story.id, {
    type: 'split-message', summary: 'The character is still typing the next message segment.',
    notBefore: sendAt.toISOString(),
    payload: { content: segment, visibleMessage: true, ... },
  }, now, participant.id)
  this.scheduleDueIntentWake(story.id, sendAt)
}
```

Consequences that follow from persistence (all quoted below in §3/§6):
- a new user message can **cancel** not-yet-sent segments (`cancelPendingOutgoingMessages`);
- a restart mid-typing **resumes** them (they are rows, not timers);
- delivery is capped at **one segment per wake-up** (`service.ts:2502-2505`, `.slice(0, 1)`),
  so a stalled scheduler does not fire a burst and lose the typing illusion.

Typing delay is model-invisible but logged, and bounded:

```ts
// service.ts:4160-4168
const baseSeconds = Math.max(0, this.config.runtime.typingBaseDelaySeconds ?? 1)
const charactersPerSecond = Math.max(1, this.config.runtime.typingCharactersPerSecond ?? 8)
const maximumSeconds = Math.max(baseSeconds, this.config.runtime.typingMaxDelaySeconds ?? 12)
const nominal = Math.min(maximumSeconds, baseSeconds + Math.ceil(nextSegment.length / charactersPerSecond))
const jitter = Math.max(0, Math.min(0.5, Number(this.config.runtime.typingJitterRatio ?? 0.3) || 0))
const factor = jitter ? 1 + (Math.random() * 2 - 1) * jitter : 1
return Math.max(250, Math.min(maximumSeconds * Time.second, Math.round(nominal * factor * Time.second)))
```

### 1.4 Comparison with `deliverImChunks` / `deliverToIm`

Our chunking is **more capable than the reference's** — this is not a gap:

```js
// im.js:244-283 (abridged)
export async function deliverImChunks({ service, binding, messages, chunking = {}, timeoutMs, signal }) {
  if (!binding?.botId || !binding?.targetId) return { ok: false, sent: 0, sentCount: 0, error: 'no-binding' }
  const send = typeof service?.send === 'function' ? service.send : null
  if (!send) return { ok: false, sent: 0, sentCount: 0, error: 'dsh-im-unavailable' }
  ...
  for (const [index, text] of list.entries()) {
    if (signal?.aborted) return { ok: false, sent: sentCount, sentCount, error: 'cancelled' }
    if (index > 0 && gap > 0) await delay(gap)
    const timeoutSignal = AbortSignal.timeout(timeout)
    ...
    // 服务返回 { sent: true } 才算确认；静默返回值一律当作未确认，宁可重试也不假装送达。
    if (result?.sent !== true) {
      return { ok: false, sent: sentCount, sentCount, error: 'delivery-not-confirmed' }
    }
    sentCount += 1
  }
  return { ok: true, sent: sentCount, sentCount }
}
```

We have per-segment timeouts, `AbortSignal` composition, and an explicit
delivery-confirmation contract (`result.sent !== true` ⇒ not confirmed). The reference
has none of these; it trusts `bot.sendMessage` to resolve.
Our semantic chunker (`splitImText`, `im.js:166-185`) with narration stripping, sentence
splitting, surrogate-pair-safe width cutting, and lossless `packMessages` (`im.js:146-155`)
is strictly richer than `content.split('<sep/>')`.

**What we lack is not the transport call — it is the durable queue the transport call
is issued from.** Concretely, in our `deliverToIm`:

```js
// index.js:1240-1259 (abridged)
const result = await deliverImChunks({ service, binding, messages, chunking: chunkingCfg, timeoutMs: resolveImTimeout(cfg.im ?? {}) })
state.lastImDelivery = { at: ..., reason, binding, ok: result.ok, sentCount: result.sentCount, total: messages.length, error: result.error ?? null }
if (result.ok) state.lastAssistantAt = Date.now()
saveState(key, state)
return result
```

`deliverImChunks` returns `sentCount`, so we **know** how many segments landed — and then
we throw that information away into a log field. The unsent tail is not persisted
anywhere. Recovery relies on the caller:

```js
// index.js:1676-1683
} else if (target.attempts >= 3) {
  target.status = 'failed'
  ...
} else {
  target.status = 'pending'
}
```

The intent returns to `pending`, which means the **next scan re-runs the whole
`handleProactive` turn** — re-waking the agent, re-invoking the model, and having it
*rewrite* the message from scratch. Partial delivery therefore produces either a
duplicate prefix (segments 1..k already landed and are sent again, if the model happens to
reproduce them) or silent divergence (model writes something different). We also do not
record what was already sent, so `sentCount` is unrecoverable after the fact.

## 2. Scheduling

### 2.1 What triggers a turn (reference)

Three triggers, all converging on `sweep()`:

```ts
// service.ts:560-562
const sweepInterval = Math.max(1, this.config.runtime.sweepIntervalMinutes)
this.ctx.setInterval(() => void this.sweep().catch(...), sweepInterval * Time.minute)
if (this.memoryConfig.enabled || this.schedulePreplanConfig.enabled) this.ctx.setInterval(() => void this.compactStories().catch(...), Math.max(1, this.memoryConfig.backgroundIntervalMinutes) * Time.minute)
```

1. **Periodic sweep** — `sweepIntervalMinutes`.
2. **Due-intent wake** — a precise timer per story (`scheduleDueIntentWake`, §2.3).
3. **Incoming user message** — buffered then flushed (`bufferUserNarrative`).

### 2.2 When does the character speak? The auto-advance cadence


The interval is **jittered per decision**, and quiet hours **replace** the interval
rather than merely suppressing sends:


40 ± 5 min. The rest-window test handles midnight wrap correctly:

### 2.3 Precise wake-ups, not just polling

```ts
// service.ts:3676-3710 (abridged)
/** Wake the scheduler close to a short typing delay instead of waiting for
 * the normal background sweep. The due intent remains the source of truth. */
private scheduleDueIntentWake(storyId: string, notBefore: Date) {
  const delay = Math.max(0, notBefore.getTime() - Date.now())
  const existing = this.dueIntentWakeTimers.get(storyId)
  // Several <sep/> segments can be scheduled at once. Keep the earliest wake-up.
  if (existing && existing.dueAt <= notBefore.getTime()) return
  if (existing) existing.cancel()
  const wake = () => {
    this.dueIntentWakeTimers.delete(storyId)
    if (this.databaseResetting) return
    void (async () => {
      const due = await this.dueIntents(storyId, new Date())
      if (due.length && due.every(intent => intent.type === 'split-message')) {
        await this.deliverDueSplitSegments(storyId)
        return
      }
      if (this.sweepRunning || this.hasPendingNarrative(storyId)) {
        const retry = this.ctx.setTimeout(wake, Time.second)
        this.dueIntentWakeTimers.set(storyId, { cancel: retry, dueAt: Date.now() + Time.second })
        return
      }
      await this.sweep()
    })().catch(...)
  }
  const timer = this.ctx.setTimeout(wake, delay)
  this.dueIntentWakeTimers.set(storyId, { cancel: timer, dueAt: notBefore.getTime() })
}
```

Four properties worth extracting:
- **One timer per story**, earliest-wins (`if (existing && existing.dueAt <= notBefore.getTime()) return`).
- **The timer is an optimization, not the source of truth** — the comment says so
  explicitly; the intent row is authoritative, so a lost timer costs only latency.
- **Busy scheduler re-arms at +1s** rather than dropping the wake.
- **Split segments bypass the narrator** and take a direct delivery path.

### 2.4 Comparison with our scan + intent timers

We have the same three trigger classes and a genuinely equivalent precise-timer design —
`scheduleIntentWake` (`index.js:1403-1421`) with earliest-wins, `rearmFromState`
(`index.js:1437-1444`) for self-healing, and `MAX_TIMER_DELAY_MS` chunking for delays
beyond `2**31-1` ms (`index.js:1389`). Our `wakeAtFor` correctly folds in the grace
period so a timer at exactly `dueAt` doesn't no-op (`index.js:1398-1401`). **This part is
already at parity or better.**

The real scheduling gaps are:

**(a) Jitter is applied as a one-sided positive offset, not a symmetric band.**

```js
// index.js:1732-1734
const interval = Math.max(5, cfg.runtime?.autoAdvanceIntervalMinutes ?? 40) * MINUTE
const jitter = Math.max(0, cfg.runtime?.autoAdvanceJitterMinutes ?? 5) * MINUTE
const threshold = interval + (jitter ? (Math.random() * jitter) : 0)
```

Reference: `config.intervalMinutes + randomInteger(-jitter, +jitter)` (`service.ts:6761`).
Ours can only ever lengthen the interval, mean 42.5 min vs. reference 40 min. Two more
divergences in the same expression: we floor the interval at **5 min** where the reference
floors at **1 min** (`service.ts:4181`), and we measure from `lastAssistantAt`
(`index.js:1735`) rather than from a persisted `nextAdvanceAt` — so any assistant message
from *any* cause resets the cadence.

**(b) No conversation follow-up passes.** We have no equivalent of `[10, 20]`-minute
post-conversation continuity (`service.ts:6764-6769`, `4272`). Our cadence resumes only
after a full `interval` from the last advance.

**(c) Quiet hours suppress rather than stretch.**

```js
// index.js:1737
if (inRestWindow(now, zone, cfg.runtime?.restWindows ?? [])) return
```

Reference `automaticIntervalMinutes` returns `randomInteger(120, 240)` during the window
(`service.ts:6760`) — the reference *keeps writing at low frequency*, we stop entirely.
Whether that is better is a product call, but it is a behavioral difference, not a
port. Also note our `restWindows` default is `[]` (`index.js:1737`), while the reference
defaults to an enabled `23:00–07:00 night sleep` window (`service.ts:4185-4188`).

**(d) No scheduling-time anchoring to a plan.** The reference can pull the next advance
earlier to land on a schedule transition:

```ts
// service.ts:4309-4314

  const schedule = await this.getSchedulePreplan(story.id)
  const transition = nextSchedulePreplanTransition(schedule, now, story.setting.timezone, 12)
  return transition && transition > now && transition < ordinaryNext ? transition : ordinaryNext

```

**(e) Write-cadence and speak-cadence are not separated as cleanly.** We do split
`lastAutoAdvanceAt` from `lastAutoMessageAt` (`state.js:82-92`) and gate speech through
`decideAdvanceDelivery` (`index.js:1820-1830`) — good. But the reference's advance gate is
three-valued (`automaticDue`, `pausedForConversation`, `dueFollowUps`) and evaluated in one
place (`service.ts:2560-2569`), whereas ours is spread between the scan guard and
`handleAutoAdvance`.

## 3. Concurrency and consistency

This is the largest structural gap, and there are **three** separate mechanisms in the
reference. We have one.

### 3.1 Per-story serial queue (we have an equivalent, but narrower)

```ts
// service.ts:485-489
/**
 * 同一故事的用户消息、到期意图和后台压缩必须串行。否则“用户新消息
 * 取消旧延迟回复”可能与定时发送同时发生，造成过期消息仍被发出。
 */
private queues = new Map<string, Promise<unknown>>()
```

```ts
// service.ts:5371-5381
private serial<T>(id: string, task: () => Promise<T>) {
  // catch 保证前一次失败不会永久堵住同一故事；finally 语义通过 then 的两个分支释放队列。
  const previous = this.queues.get(id) ?? Promise.resolve()
  const current = previous.catch(() => undefined).then(task)
  this.queues.set(id, current)
  void current.then(
    () => { if (this.queues.get(id) === current) this.queues.delete(id) },
    () => { if (this.queues.get(id) === current) this.queues.delete(id) },
  )
  return current
}
```

Note the **re-entrancy hazard documented at the compaction call site** — a promise-chain
serial cannot be re-entered from inside one of its own tasks:

```ts
// service.ts:4634-4638
// Phase 1 (serial): cheap reads and due checks. The queue MUST be
// released before the compactor call — a promise-chain serial cannot
// be re-entered from inside one of its own running tasks (that
// deadlocks the whole story queue), so the expensive model call runs
// unqueued and only the cheap DB writes re-acquire it afterwards.
```

This becomes a three-phase pattern (§5). Our `inFlight` map (`index.js:1912-1921`) covers
the sweep-entry exclusion correctly, including the subtle "periodic sweep skips, one-shot
timer must not skip" rule (`index.js:1959-1974`). But it protects only the *entry point* of
`handleSession`; it does not serialize the mutations that happen inside.

### 3.2 Global database write queue (we have **nothing** equivalent)

```ts
// service.ts:508-509

```

```ts
// service.ts:5383-5387
```

(`service.ts:5506-5512`), so **no two writes in the process ever interleave**, regardless of
which story or which async path they came from. Reads stay concurrent and only get a
bounded retry:


Our counterpart is a bare atomic-rename with a **swallowing catch**:

```js
// state.js:124-137

    const dir = interludeHome()
    fs.mkdirSync(dir, { recursive: true })
    const file = path.join(dir, `${safeFileName(key)}.json`)
    const tmp = `${file}.tmp`
    if (state && typeof state === 'object') state.sessionId = String(key)

```

Two distinct issues, both real:

1. **No serialization.** `saveState` is synchronous, so a single write is atomic *within*
   the event loop. But `loadState` → mutate → `saveState` is **not** atomic as a
   read-modify-write sequence, and our code does this from several async paths
   (`handleProactive`, `handleAutoAdvance`, `recordMissedCommitment`, tool handlers).
   Since the scan runs sessions **concurrently** by design
   (`index.js:1958-1975`, `Promise.all(jobs)`), two concurrent writers on the same key
   can lose an update. Our only guard is the per-key `inFlight` — which, as noted, does not
   cover tool handlers or `session/event` listeners.
2. **All errors are silent.** A failed write means an intent is lost with no signal. The
   reference at least logs on final failure (`service.ts:5446`).

There is a real bug class here that the reference prevents by construction: we can
`saveState` a stale in-memory snapshot over a newer one, losing a `delivered`/`settled`
marker and re-delivering.

### 4.2 What our single JSON doc can and cannot represent

Our state is one flat document per session (`state.js:48-98`), with cap-based retention:

```js
// state.js:24-26
const STATE_VERSION = 1
const MAX_INTENTS = 40
const MAX_FACTS = 200
```

**Can represent (genuinely at parity):** story canon, continuity, facts with
importance/confidence, overlay entries, intents with `dueAt`/`status`, agency window,
proactive drafts + fingerprints, alter state, preplan, day-scoped `reachedOut` quota.

**Cannot represent — with the specific mechanism that is missing:**

1. **Append-only history.** We have no `script_entry` equivalent at all. `state.js:7-9`
   states this is deliberate: *"互动时序…不落盘，直接从 session 日志增量折叠"*. That
   aligns with DSH's log-is-truth invariant and is defensible — but it means **there is no
   durable record of what the character actually said on a proactive delivery**, only
   `lastImDelivery` (a single overwritten slot, `index.js:1248-1256`). The reference can
   answer "has this exact text already been delivered, and did the platform accept it?"
   (`confirmOutgoingDeliveries` → `character-message` entry with `messageId` in metadata);
   we cannot.
2. **Per-entry kind/actor/visibility.** The reference distinguishes
   `user-message`, `character-message`, `script`, `group-message`,
   `character-group-message`, `outgoing-delivery-failed`, `intent-cancelled`,
   `stream-finalization-failed` (`service.ts:41`, `4106`, `3968`, `2361`). We have no
   entry level, therefore no *visibility* filter, therefore no per-participant privacy
   projection (`isHistoryEntryVisibleToParticipant`, `service.ts:54-56`).
3. **Proposal/provenance for state changes.** `interlude_state_patch` carries `evidence`,
   `confidence`, `impact`, `status`, `sourceEntryIds`. Our `upsertOverlay` keeps a single
   `evidence` **counter**:
   ```js
   // state.js:294-306
   const entry = { id: ..., layer, content, evidence: (existing?.evidence ?? 0) + 1, appliedAt: now }
   state.overlay = [...(state.overlay ?? []).filter(item => item.layer !== layer), entry]
   ```
   We cannot audit *which* events justified a change, cannot hold a proposal pending, and
   cannot roll back.
4. **Relational multiplicity.** Our doc is keyed by session. The reference's
   `interlude_participant` is a **separate row per DM account** with its own `state`,
   `relationship`, `profile`, `personId`, linked to a shared story
   (`database.ts:50-55`). We model this only as `agencyWindow`/`reachedOut` on the single
   session — so a shared story across accounts (reference: `sharedStoryConfig`) has no
   representation. `state.js` has no participant list.
5. **Indexed query.** `database.ts` declares indexes on `storyId`, `status`, `notBefore`,
   `importance`, `occurredAt`, `confidence`, `periodEnd`, `validThrough`. Our `dueIntents`
   is a linear scan over a capped 40-element array (`state.js:251-255`). Fine at our scale
   — the point is that the reference's shape is what allows intents to be *queried by due
   time across stories* rather than replayed.
6. **Tiered overlay archive.** `overlay_snapshot` holds `weekly`/`monthly` tiers with
   `sourcePatchIds` (`database.ts:124-128`). Our overlay is one entry per layer
   (`state.js:304`), permanently overwritten.
7. **Sticker/media catalog with embeddings and hash-based dedup** (`database.ts:133-138`).
   We have none.
8. **Schedule preplan as a first-class row** with `regimes`/`exceptions`/`validFrom`/
   `validThrough`/`lastReviewedLocalDate` (`database.ts:143-148`). Ours is a single opaque
   `preplan` blob (`state.js:96`).

**Where our model is better:** the reference's `interlude_story.state` and
`interlude_participant.state` are `json` columns — untyped blobs inside a typed schema —
and it has a whole `normalizeDatabaseRow` / `DATABASE_DATE_FIELDS` layer to repair dates
on read (`service.ts:6609-6635`). We serialize real JS values with `JSON.parse`/`stringify`
and have no date-coercion layer. Also, our `STATE_VERSION` gate (`state.js:106`) gives us a
clean versioning story that the reference lacks.

### 5.5 Our position

We do no compaction and defer to DSH — no scene/arc/fact/journal tiering, no evidence
thresholds, no overlay archival. This is a stated design decision, not an oversight, and
**the honest framing is that we are not "missing" compaction so much as missing the
*retrieval budget* that makes it necessary.** The reference compacts because it must fit a
scene's raw entries into a prompt under `compactionCharacterLimit: 32_000`; our context is
assembled by DSH per turn.

However, two pieces are worth separating out as genuinely transferable **because they cost
nothing and prevent observable errors**:

- **`lastEntryId` as an incremental checkpoint** — we already track `lastSeenSeq` in
  `foldFromLog` (`state.js:212-226`), which is the same idea. We are fine here.
- **Evidence-gated state patches.** Our `upsertOverlay` increments a counter and applies
  immediately (`state.js:294-306`). There is no minimum-evidence, no cooldown, no
  major/minor distinction. This is a *correctness* concern independent of compaction: the
  model can rewrite a character's core traits on a single weak turn. The reference's
  `statePatchMinTurns: 3`, `statePatchMinDays: 2`, `statePatchCooldownHours: 72` are pure
  guards that need no summarization model to adopt.

**At-least-once is repaired, not ignored** — a write that "failed" may already have
committed, so the reference looks for the logical row before retrying:


Compare our network-failure handling:
- Our IM delivery has timeouts and confirmation (§1.4) — **better than the reference**.
- Our persistence has `catch {}` with no retry and no logging (`state.js:134-136`) —

- Our model call has no bounded retry.

Three separate recovery mechanisms.

**Backoff map is in-memory only** — a restart clears it, which is the desired behavior:


with `const SCHEDULE_PREPLAN_RETRY_BACKOFF = 2 * Time.hour` (`service.ts:74`).

**Split segments survive restart because they are rows, not timers.** The timer is
rebuilt on demand by `scheduleNextSplitWake` (`service.ts:3714-3720`), and the sweep picks
up anything overdue. Delivery is capped at one per wake (`service.ts:2502-2505`), so a
long outage produces a paced replay, not a burst.

**Guards against operating on a half-reset database:**


checked at every entry point — `sweep` (`2460`), `receive` (`1284`), `flushGroupTurn`

## 7. Prioritized transferable improvements

Ordered by (severity of the failure it prevents) ÷ (effort to adopt).

### P0 — Persist the delivery queue so retry never re-generates content

This is the single largest gap, and it compounds with everything else.

**Problem.** `deliverToIm` (`index.js:1228-1260`) sends N chunks, learns `sentCount`,
stores it in `lastImDelivery`, and discards the unsent tail. On failure the intent returns
to `pending` (`index.js:1681-1682`), so the next scan re-wakes the agent and the model
**rewrites the message**. A partial delivery therefore yields a duplicated prefix or a
different message.

**Adopt.** Write each chunk as a persisted queue item *before* transport, with its own
`status`, `attempts`, `notBefore`, and exact `text`. Deliver at most one chunk per
wake-up, marking each `delivered` only on confirmed `sent: true`. On failure, reschedule
that exact item at +30s — resend the *text*, never re-run the model.

Reference basis: `service.ts:4084-4097` (segments become future intents) and
`service.ts:2525-2531` (retry the row at +30 s with `scheduleDueIntentWake`).

**We already have the primitives.** `state.intents` is a durable array with `status` and
`dueAt`; `deliverImChunks` already returns accurate `sentCount`; `scheduleIntentWake`
already does precise wake-ups. This is a wiring change plus a new intent kind, not new
infrastructure.

### P1 — Serialize state writes and stop swallowing write errors

**Problem.** `saveState` (`state.js:124-137`) has no queue and a bare `catch {}`. Our
concurrent `Promise.all` scan (`index.js:1975`) plus tool handlers and `session/event`
listeners mean the same key can be written by overlapping read-modify-write sequences,
and the per-key `inFlight` does not cover the non-sweep paths. A lost write can drop a
`delivered` marker, causing re-delivery of an already-sent message.

**Adopt.** A module-level promise chain exactly as `service.ts:5383-5387`, plus bounded
retry with jitter (`service.ts:5450-5452`) and a real error report instead of silence.
Sync `fs` makes each individual write atomic; the queue is what makes the *sequence*
atomic.

**Also adopt the "did my write land?" reconciliation** (`service.ts:5476-5504`): before
retrying a failed write, re-read and look for the logical row. Cheap, and it is the
difference between at-least-once and duplicate intents.

### P2 — Bound and persist narrative retries

**Problem.** On write-back failure we consume no interval (`index.js:1802-1815`, which is
correct) but schedule **no retry at all**. Recovery depends on the next periodic scan.

**Adopt.** `scheduleNarrativeRetry`'s shape (`service.ts:3633-3652`): retry at
`narrativeRetryDelaySeconds` (default 60), `narrativeRetryMaxAttempts` (default 6), cancel
any prior pending retry first so exactly one is outstanding, and log the attempt count.
This is a small, self-contained addition to `handleAutoAdvance` and `handleProactive`.

### P3 — Evidence-gated overlay changes

**Problem.** `upsertOverlay` (`state.js:294-306`) applies any model-proposed change
immediately, with only a counter as provenance. One weak turn can overwrite a character's
core traits — an unrecoverable canon corruption.

**Adopt.** The threshold triple from `service.ts:4531-4534`: `statePatchMinEvidence: 3`,
`statePatchMinTurns: 3`, `statePatchMinDays: 2`, plus `statePatchCooldownHours: 72`. Stage
proposals with `status: proposed` and apply only when all gates pass. This needs no
summarization model, so it is independent of our decision to defer compaction to DSH.

### P4 — Lossless interruption: cancel with content carry-forward

**Problem.** We have no equivalent of "the user interrupted mid-typing." Our capture
window is a timeout (`capture.js:93-94`), not a revision. A superseded turn's text is lost
or re-generated.

**Adopt.** The pattern at `service.ts:3960-3973`: when cancelling pending outgoing items,
persist their exact text as a system entry that says the protagonist *wanted to send* it,
so the next turn can finish the thought. Pair it with the safety rule at
`service.ts:6592-6600` (`shouldSupersedeNarrativeRequest`) — never cancel after the first
message has been committed, because the user has already seen part of it.

### P5 — Scheduling polish (low effort, clear wins)

Four small changes, all in `handleAutoAdvance`:

1. **Symmetric jitter** — replace `interval + Math.random() * jitter`
   (`index.js:1734`) with `interval + randomInteger(-jitter, +jitter)`
   (`service.ts:6761`). Removes a systematic +2.5 min bias.
2. **Floor at 1 min, not 5** — `index.js:1732` vs. `service.ts:4181`.
3. **Stretch in quiet hours rather than stopping** — return
   `randomInteger(120, 240)` minutes instead of `return` (`index.js:1737` →
   `service.ts:6760`), and default `restWindows` to the `23:00–07:00` window the reference
   ships (`service.ts:4185-4188`).
4. **Persist `nextAdvanceAt`** and gate on it (`service.ts:4224-4232`) instead of deriving
   the cadence from `lastAssistantAt`, so an unrelated assistant message cannot reset the
   schedule.

### P6 — Append-only delivery record

**Problem.** `lastImDelivery` (`index.js:1248-1256`) is a single overwritten slot; we
cannot answer "was this exact text already delivered to this target?"

**Adopt.** A bounded append-only list of confirmed deliveries with timestamp, target,
text hash, and the platform's confirmation. This is what makes P0 verifiable (did the
retry duplicate?), and it is the minimal slice of `script_entry` that earns its keep
without importing the full 13-table model. Note this is *new* history we would be
recording, not a violation of our "log is truth" stance — proactive deliveries do not
appear in the DSH session log as user-visible events.

### Explicitly NOT recommended

- **Porting the 13-table schema.** Our single-document model is right for one session =
  one story. The reference's relational shape exists to support multi-account shared
  stories and indexed cross-story queries we do not have.
- **Porting compaction.** Not needed while DSH assembles context. Revisit only if prompt
  budgets become a measured problem — and if so, port `scene`/`arc`/`lastEntryId` first,
  not the overlay tiering.
- **Porting the OneBot surface** (stickers, native faces, reactions, voice, CQ parsing).
- **Porting `blindMode`** — its `healthReportMinutes` interval and health-flag machinery
  (`service.ts:563-565`, `5270-5272`) solve a Console-logging-visibility problem we do
  not have.
