## 二、方案里**判断有误**的地方（已按实情处理）

这几条是实际动手时发现的，与方案描述不符。记在这里，免得下次又照着错的前提做一遍。

### 1. 「入站附件清洗 ❌未同步」——其实早已实现
`lib/qq-im/inbound.js` 的 `sanitizeAttachments` 完整处理了 CDN / `rkey` / base64
泄漏。方案标「⚠️ DSH 有部分处理」，实际是**完整**的。无需改动。

### 2. 「日程主键冲突（v0.1.5-beta4）」在本架构下不存在
上游该 bug 在 SQLite 层（`database.ts`）。DSH 用 JSON + `withStateLock`，
**架构上不可能发生**。方案标 🔴 高优先级并列入 Phase 1.1——照做就是打空气。

### 3. 「后台压缩失败冷却」不在 `preplan.ts`，在 `service.ts`
真实实现在 `service.ts` 的 `COMPACTION_RETRY_BACKOFF = 2h`。方案把它挂到了
`preplan.js` 上。**已按真实位置实现为 `timeline-guard.js`**（见 §三.1）。

### 4. 「clock 的 12 小时制歧义 / 6 小时视野」在 `time.ts` 里并不存在
上游 `time.ts` 全文只有 4KB，没有歧义处理逻辑；`TIME_FORWARD_HORIZON_MINUTES`
在 `service.ts`。且本地 `clock.js` 用 `hourCycle: 'h23'`，**歧义在架构上不存在**。
方案标的两项均未做——做了也是空转。

### 5. Phase 1.4「Story State 对齐 v3」是伪工作
本地 `state.js` **早已有** `workingDetails` / `scenePresence` / `timelineCarry` /
`extensions`。缺的只是 Script-First 专属字段（`sceneFrame` / `dialogueBurst`），
而那些**没有对应功能时就是死数据**。实际做法是按需增量补齐，而不是「升到 v3」。

### 6. 排序依赖被写反了
方案把 `life-handoff` 排在 `scene-frame` 之后，但它其实是 scene-frame 与
knowledge-evidence 的**共同前置**（前者靠它提取场景转换，后者靠它那套逐字校验）。
实际按 `entry 层 → life-handoff → scene-frame / knowledge-evidence` 落地。

## 四、方案**漏掉**的一件关键事

长期事实（`state.facts`）**从来没有进过提示词**——只有人工 `/interlude context`
能看见。也就是说 Phase 2 做的认知证据、词法召回，**在当时都没有下游**：标了
`belief` / `confirmed` 也没人读。

方案在 §3.2 讨论「认知证据」时只说了要「在 `rankFacts` 评分中让 `confirmed`
权重更高」，但没指出**事实压根没有被注入**这个前提。

已补：`renderFacts` + 按 `memoryLimit` 注入，且**她的解读会被显式标注**，
不与已确认的事实平铺。

## 六、过程中发现并修掉的真问题

这些不是「照方案做」，而是做的过程中**方案与差分核验都发现不了、只有真插件跑一遍才暴露**的：

1. **`character-message` 此前永远不会产生**。DSH 里「写出的正文」与「发出去的话」
   是两件事：`assistant/message` → `script`（叙述），只有 `interlude_say` 才是
   真实说出的话。原实现只记了前者，于是 `confirmed` 在真实链路上**永远不可能成立**。

2. **场景帧只在「有新条目」时重投影**。于是「这一轮没有新日志、但
   `interlude_handoff` 刚改了在场名单」时帧永远是旧的——证据变了帧没变。

3. **`rankFactsByRecall` 对部分命中无效**。三次迭代：加权平均压不住首位、
   乘数削弱救不了末位（`base=0` 恒为 0）、加法项与首位保底分打平。
   最终用**两级排序**（先分「有没有命中」，组内再比分数）。

4. **`recordDirectorFailure` 改了副本而不是原对象**。`normalizeTimelineGuard`
   返回的是副本，于是失败计数根本没涨、熔断永远不会触发——保护机制静默失效。
