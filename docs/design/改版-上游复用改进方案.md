# 上游复用改进方案：QQ-agent + hds-interlude → dsh-hds-interlude

> 分析对象
> - 上游 A：<https://github.com/K0nd1us/QQ-agent>（v0.3.0，Node≥20 + Electron，**MIT**）
> - 上游 B：<https://github.com/euphoriaaaaaa1/hds-interlude>（v0.1.4，Koishi 插件，**AGPL-3.0**）
> - 本地：`dsh-hds-interlude`（DSH/Cordis 插件，**AGPL-3.0**）
>
> 分析方式：两仓库已浅克隆到 `.ref-analysis/`，逐文件读源码 + 交叉验证，非文档推测。

## 〇、先说结论

本地项目**已经**从上游 B 完成了主力移植（`preplan.js` / `agency.js` / `alter.js` 是逐行级移植，
`docs/design/对比-hds-interlude全面对比与改进.md` 已记录五项落地改进）。
所以本方案的增量不在「再抄一遍 B」，而在三件事：

| 方向 | 来源 | 为什么值得 |
|---|---|---|
| **A. 上游 A（QQ-agent）的零耦合模块** | MIT，可自由取用 | 本地**完全没有**对 A 做过复用，而 A 有几个生产级独立模块 |
| **B. 上游 B 的 P1–P4（上一轮明确列为「值得做但没做」）** | 本地自己的路线图 | 纯计算，不依赖拿不到的能力，价值已论证 |
| **C. 上游 B v0.1.4 的 cache-first 契约恒量化** | 上游文档级设计 | 本地**结构上做不到**大部分，但有一条能做 |

**许可证要点**：本地是 AGPL-3.0，上游 B 也是 AGPL-3.0 → 兼容，直接移植即可（现状已如此）。
上游 A 是 **MIT** → 可自由引入，只要保留版权声明。**这是本方案能成立的前提。**

### 1.2 逐条落点

#### 【A-1】SSRF 防护 → 引入 `safe-fetch.js`（P1，最值钱）

本地 QQ 通道（`lib/qq-im/`）目前收图、发图、可能网页抓取，**没有任何 SSRF 防护**。
上游 A 这份是整个仓库质量最高的模块：

- `isPrivateIp()` 覆盖极全：`10/127/0/169.254/172.16-31/192.168/**100.64-127 CGNAT**/198.18-19/192.0.0/24/≥224`，
  IPv6 覆盖 `::1`、`fc/fd` ULA、`fe8-feb` 链路本地、`2001:db8`、`ff` 组播，
  以及 `::ffff:` / `64:ff9b` NAT64 / `2002:` 6to4 的**内嵌 IPv4 递归解析**；
- `resolveSafeHost()` DNS 解析后**检查全部结果**，任一私网即拒；
- `requestOnce()` **把 hostname 换成已校验的 IP 发请求**，同时保留 `Host` 头与 https `servername`(SNI)
  → **从根上消除 DNS rebinding**；
- 手动跟重定向（≤5 跳），**每一跳重新校验**；
- `readBounded()` 按**字节**限读（不是字符，避免中文误判 truncated）。

**落点**：新增 `lib/net/safe-fetch.js`，把 2 处 `getConfig()` 改成参数注入
（`allowPrivate` 由调用方传，对应本地 `im.*` 配置）。QQ 入站图片与 `interlude_say` 的附件下载改走
`safeFetchBinary`；任何由模型/用户提供的 URL 走 `validateImageUrl`。

**成本**：约半天。**收益**：消除一个真实的内网探测面（本地跑在用户机器上，风险高于云部署）。

#### 【A-2】串行写队列 → 修掉本地 P1「静默丢写」

本地 `lib/state.js:124-137` 的 `saveState` 是：

```js
} catch {
  /* 持久化是尽力而为的 */
}
```

`docs/design/对比-hds-interlude全面对比与改进.md` 已把它列为 **P1**：并发扫描（`Promise.all`）
+ 工具处理器可能对同一 key 做并发读改写，`inFlight` 只挡扫描入口、**不覆盖工具路径**。
一次丢写丢掉 `delivered` 标记就会**重复投递**。

上游 A `util.js:147-155` 有一个 7 行的现成实现：

```js
export function createSendChain() {
  let chain = Promise.resolve();
  return function enqueue(task) {
    const next = chain.then(task, task);   // 失败也继续链
    chain = next.then(() => undefined, () => undefined);
    return next;
  };
}
```

上游 B 对应的是 `service.ts:509` 的 `databaseWriteQueue` + `retryDbWrite`（7 次退避重试
`[100,250,500,1000,2000,3000,5000]` + 抖动）。

**落点**：`lib/state.js` 新增 `writeChains: Map<key, enqueue>`，`saveState` 改为入队；
`catch` 从静默改为 `console.warn` + 计数器（不照抄 7 次重试，但**不能静默**）。
**不要**重写整个存储层——本地 B 的分析已判定「一个 JSON 文档足够，DSH 没有 `ctx.database`」。

#### 【A-3】弱模型容错 → `parseInlineToolCalls` / `extractJsonObject`

本地依赖模型的 `interlude_say` / `interlude_plan` 工具调用。**模型忘记调工具**是本地已知故障模式
（`commitmentBackstop` 就是为此而生）。上游 A 有实战代码：

- `parseInlineToolCalls`（`orchestrator.js:1120`）支持**三种**弱模型格式：
  XML `<function=..><parameter=..>`、整块 JSON、函数名 + JSON；
  且会**回填 messages 把 assistant 改成 tool_calls 形态**（否则后续请求报错）；
- `extractJsonObject`（`:1193`）**五层降级**：直接解析 → 剥 ``` 围栏 → 取首 `{` 到末 `}` → 修尾随逗号/单引号 → 正则兜底。

**落点**：`lib/` 新增 `parse-inline-tools.js`，接入本地「工具没被调用」的兜底路径
（现在 `commitmentBackstop` 用文本启发式，可以先用这套解析器试一遍，命中率更高）。

#### 【A-4】模型能力字典 → `model-vision-docs.js`

本地 `docs/design/` 有一篇《诊断-图片发不了-模型能力声明》，说明**模型是否支持图片输入**是个反复踩的坑。
上游 A 有一张 403 行的内置资料表：`PROVIDER_DOCS`（链路是否透传图片）+ `MODEL_DOCS`（厂商官方能力），
模型 ID 归一做了小写化 + **斜杠前后双键匹配**（`deepseek-ai/xxx` ≡ `xxx`），每条带 `note` 注明来源 URL。

**落点**：作为只读参考表引入，用于 `lib/qq-im/outbound.js` 发图前的能力判断。
本地已有 `diagnose-*` 经验，这张表可直接替换手写判据。

#### 【A-5】档位前置判定（架构借鉴，非直接搬）

上游 A **省 token 的真正来源**不是提示词更短，而是 `orchestrator.js:228-262` 这个顺序：

1. `#predictTier()` 用 `peekUnread`（**只看不取**）预判；
2. 若不响应 → `markAllRead()` **标记已读但不取走**（内容留档，日后作历史），
   **不建会话、不调模型**；等待中的会话**干净消失**（不标"中止"）；
3. 命中才 `drainUnread()`。

关键巧思：**预判不消费未读** → 防抖窗口期内每条新消息都能重新预判
（先来闲聊→不命中，接着有人 @ →命中，立刻显示）。

**本地对应**：`lib/index.js` 的 `handleProactive` / 主动扫描路径。本地是「距上次够久就唤起模型」，
**不管这段时间有没有发生什么**。B 自己的 token 文档（`对标-hds-interlude的token策略.md`）已建议过
「没证据就别调模型」，这条是它的完整实现参考。

## 三、上游 B v0.1.4 的 cache-first：我们能拿走的那一条

上游 `docs/development/2026-08-31-payload-cache-first.md` 记录了两个改动。**要精确区分能做与不能做**：

### ❌ 不能做：payload 重排

它把 34 个 JSON 顶层字段按**变异频率**重排（稳定区 `setting→recentScript→durableFacts→…`，
每轮变化区 `…→currentEvent→recentExchange`），因为 legacy 顺序下「system 之后第一个 token 就分叉」，
服务商前缀缓存**永远无法命中**。

本地**结构上做不到**：DSH 拥有请求组装权，本地只能 `agent/pre-step` 追加消息。
（本地自己的实测反而显示 DSH 的前缀缓存本来就很好：同模型连续对话命中率 **97~99%**，
真正的元凶是**会话中途换模型**——一次切换让约 10 万 token 从缓存价变全价。）

### ✅ 能做：**系统提示恒定化**

上游同文档的第二个改动是真金白银，且**不依赖任何上游独有能力**：

> `refreshContinuity` 双变体恒定化：原来系统提示在 refresh 轮与非 refresh 轮使用两条不同文本，
> **每 15 轮击穿一次整个前缀缓存**。现合并为一条恒定行，由 payload 的 `refreshContinuity` 标志驱动行为。
> 系统提示自此跨全部轮次**逐字节一致**。
> 实测净账：非 refresh 轮 12,899→12,648 字符；**refresh 轮 13,093→12,648**；
> 主要收益不是静态缩减，而是**系统提示恒定化**（省约 16k tokens 重填，摊薄约 1.1k tokens/轮）。

**本地落点**：`lib/render.js` 的 `renderCanon` / `renderRules` / `storyRules`。
已确认本地有**按场景切换文本**的做法（`storyRules(deliverable)` 就有两个分支、
`renderRules` 有 `imActive` 条件段落）——**凡是「每 N 轮才变一次」的条件段落，都是周期性击穿缓存的元凶**。

**行动**：审计 `render.js` 所有条件分支，把「文本二选一」改成「文本恒定 + 用一个短标志行驱动行为」。
这一条与上游 B 的做法一字不差地对应，且完全在本地能力范围内。

## 六、一句话总结

本地已经榨干了上游 B 的**主叙事移植**，但留下了两条尾巴：
**P1（静默丢写）和 P3（人格漂移）尚未做，且都是纯计算、零依赖**——应该立刻做。

同时，本地**从未复用上游 A**，而 A 是 MIT 许可、且有几个真正零耦合的生产级模块，
其中 `safe-fetch.js` 的 SSRF 防护是本地作为一个**跑在用户机器上**的插件最缺的一块。
先搬那 5 个模块里最值钱的 3 个（safe-fetch / createSendChain / 弱模型解析器），
再补 B 的 P1/P3，最后做「系统提示恒定化」这条唯一在本地能力范围内的缓存优化。
