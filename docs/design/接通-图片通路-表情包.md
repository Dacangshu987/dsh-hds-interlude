# 接通图片通路：角色现在能发表情包了

> 需求：QQ 机器人发表情包 / 图片。
> 上一轮诊断结论是「出站链路是纯文本的，SDK 其实支持（`msg_type: 7`）但插件没接」。

## 一句话

新增 `interlude_send_image` 工具，图片走 `QqChannel.sendImage` → SDK `sendImage`；
**图片与文字的调用顺序就是发送顺序**，图片失败时降级成一句文字而不是让整轮发言消失。

## 关键设计决定

### 1. 为什么是两个工具而不是给 `interlude_say` 加参数

`interlude_say` 的 `text` 是「每行一条」的纯文本管线。把图片塞进同一个参数后，
「第几行是图、第几行是字」就没法表达了。拆成两个工具后，**工具调用顺序天然就是
发送顺序**——`interlude_send_image` 后接 `interlude_say` 就是「先甩图再补一句」。

### 2. 只接受 http(s) 与本地路径

`url` 会被原样交给 **QQ 服务器去拉取**。放行 `file:` 等于把「本机文件读取」
变成一次远程请求；`data:` 会把任意大小的 base64 塞进请求体。本地文件有
`localPath` 这条正路，不需要借 `url` 绕。`normalizeImageSource` 里硬性拒绝。

### 3. 图片失败降级，而不是整轮失败

模型想发表情包却发不出去时，若整轮作废，**对方会完全收不到任何回应**——
比丢一张图严重得多。所以 `onImageError` 返回文案时，该条替换成一句
`[图片发送失败]` 继续投递，并计入 `degraded`。

### 4. 向后兼容：文字条目对外仍是字符串

`deliverMessages` 内部统一成 `{kind:'text'|'image'}`，但**对外**经
`toExternalItem` 还原：文字是字符串，图片是对象。老调用方（分条路径、投递记账、
测试替身）都是按「传字符串、`remaining` 也是字符串数组」写的，统一暴露成对象会让
它们全部静默变成「发不出内容」。

## 修掉的两个既有缺陷

改这条链路时撞出两个**原本就存在**的问题：

### ① bot-command 回复被吞掉括号内容

`sendToTarget` 过去对 `text` 参数会过一遍「旁白清洗/分条」。`/status` 的回复
「已连接（测试）」里的 `（测试）` 被当旁白删掉 → 变成「已连接」。

`channel.js` 的注释其实早就写明「命令回复是系统文本，应当原样整体发出」，
所以 bot-command 路径特意用 `messages: [...]` 传。但我最初改写 `sendToTarget`
时，把 `messages` 里的字符串**又分条清洗了一遍**，等于把这个保护拆了。

**修正**：`messages` 里的是已定稿条目，一律原样发出，不再重新分条。
需要分条的调用方走 `text` 参数。修完后 `test/qq-im/bot-commands.test.mjs`
从 20/21 变成 21/21（该失败在改动前的基线上同样存在，已在 stash 后复现确认）。

### ② 承重验证的锚点失配

`test/verify-delivery-resume-loadbearing.mjs` 靠**文本匹配**把 `remaining:`
那一行抠掉，以此证明「重试不重新生成」真的有测试在管。我给那行加了
`.map(toExternalItem)`，锚点就对不上了，脚本以 exit 2 报「结构已变」。

**修正**：更新锚点。修完后该验证重新变绿，说明重试语义确实还受检验。

## 安全边界（有单测覆盖）

```
data:image/png;base64,...    → 拒绝
ftp://x.com/a.png            → 拒绝
C:/secret.txt                → 拒绝（非图片扩展名）
{url:'https://x.com/a.png'}  → 通过
{file_path:'D:/pics/a.png'}  → 通过
```

## 使用方式

模型侧（提示词已交代）：

```
interlude_send_image({ file_path: "D:/pics/开心.png" })
interlude_say({ text: "看这个" })
```

配置侧：

```yaml
im:
  imageTool: interlude_send_image   # 默认值
  imagesEnabled: true               # 关掉后模型即使调工具也发不出去
```

> ⚠️ 表情包需要模型知道文件在哪。把常用表情包放在固定目录、
> 并在角色设定或提示词里告诉它，比让它自由发挥可靠得多。

## 尚未做的（按需再说）

  （`msg_type` 里的 face 元素）是另一套协议，SDK 也没直接暴露。
