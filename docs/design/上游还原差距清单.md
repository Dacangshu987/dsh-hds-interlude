## 零、先说清「前端还原」的含义

**上游没有自建前端。** 上游仓库里没有 `client/`、`ui/`、`.vue`、`.tsx`；
它的 UI 就是 **Koishi Console 读 `src/index.ts` 的 Schema 自动生成的配置表单**。

那份 Schema 有 1332 行、按 `【必填 1】`…`【维护 20】` 分成 26 个逻辑段。

所以「还原前端」在本仓的准确含义是 **两件事**：

| # | 内容 | 说明 |
|---|---|---|
| A | **字段对齐** | 上游有的字段本仓要有（或明确记为 N/A），命名/默认值/取值范围一致 |
| B | **结构对齐** | 面板的分组顺序、标签文案、字段归组按上游 Schema 的 26 段重排 |

本仓现状：`lib/client.js`（3550 行）是另写的分页面板，`lib/schema.js`（372 行）
只有 10 个顶层段。**两边都需要按上游重排/补齐。**

## 三、可移植类（要做的）

### 3.1 提示词风格（5 个）—— 优先级最高

上游把提示词做成**可配置项**，本仓是硬编码常量：

| 上游字段 | 上游用途 | 本仓现状 |
|---|---|---|
| `mainPrompt` | 主叙事提示词覆盖 | 硬编码在 `lib/render.js` |
| `formatPrompt` | 输出格式约定覆盖 | 同上 |
| `fixedPrompt` | 固定段覆盖 | 同上 |
| `stylePrompt` | 文风段覆盖 | 同上 |
| `prompt`（Alter 段内） | Alter 侧端提示词 | `alter.js` 的 `prompt` 已有字段但可能未接线 |

**处置**：在 `lib/schema.js` 加这几个字段，`render.js` 支持「有配置则覆盖默认」。
这是**收益最高**的一批——用户能直接调教行为，且完全在插件能力圈内。

## 五、施工顺序（建议）

按「收益 / 成本」排序，每批独立可验证：

1. **提示词可配置化**（§3.1）：5 个字段，收益最高、成本最低、完全在能力圈内
2. **文本/节奏字段对齐**（§3.2）：补 `userMessageDebounceSeconds`、
   `conversationFollowUpMinutes` 等「已标未生效」的项，让旋钮真的生效
3. **StoryDefaults 结构重排**（§3.3）：字段名与上游对齐（保留旧名兼容）
4. **面板结构对齐**（§零·B）：按上游 26 段重排 `lib/client.js`
5. **ChatActions / Stickers / SharedStory 旋钮**（§2.3）：本仓已有底层，补配置面
6. **承诺机制收敛到上游**（§4）：实现 `followUpCommitment` 申报制，
   再把 `commitmentBackstop` 正则降级

## 六、验证基线

→ 更新本清单与《上游rc系列-移植台账.md》。
