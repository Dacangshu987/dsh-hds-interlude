## 零、先说清「前端还原」的含义

**上游没有自建前端。** 上游仓库里没有 `client/`、`ui/`、`.vue`、`.tsx`；
它的 UI 就是 **Koishi Console 读 `src/index.ts` 的 Schema 自动生成的配置表单**。

那份 Schema 有 1332 行、按 `【必填 1】`…`【维护 20】` 分成 26 个逻辑段。

所以「还原前端」在本仓的准确含义是 **两件事**：

| # | 内容 | 说明 |
|---|---|---|
| A | **字段对齐** | 上游有的字段本仓要有（或明确记为 N/A），命名/默认值/取值范围一致 |
| B | **结构对齐** | 面板的分组顺序、标签文案、字段归组按上游 Schema 的 26 段重排 |

本仓现状：`lib/client.js`（3550 行）是另写的分页面板，`lib/schema.js`（372 行）
只有 10 个顶层段。**两边都需要按上游重排/补齐。**

- **批次 2**：四个可配置提示词接上 schema + render + 面板。按上游段落标签

- **批次 3**：见上表 §3.2。`conversation-follow-up` 从「只被提及的死词汇」
  变成**真的会被设成该阶段**；`minimumAdvanceMinutes` 与
  `autoAdvanceIntervalMinutes` 的语义终于分开。
- **批次 4**（用户裁定「完全改成 `<sep/>` 协议」）：本仓原先是「换行即一条」，
  等价于上游把 `convertNewlineToSeparator` **打开**（那是上游 rc36 给小模型留的
  补救开关，默认关）。现在默认与上游一致：**只有分隔符才是气泡边界**。
  三个协议字段（`splitReplyMessages` / `messageSeparator` /
  `convertNewlineToSeparator`）贯通 schema → `im.js` → `qq-im/outbound.js`
  → 提示词 → 面板。
  - 关键坑：`cleanImText` 是**逐行**剥「行首尾成对引号」的，而协议下多条气泡
    同处一行（`"甲"<sep/>"乙"`）。所以必须**先按分隔符切、再逐段清洗**；
    反过来会把外层引号剥掉得到 `甲"<sep/>"乙`。
  - 超长仍按句末标点／软断点切：平台单条上限是硬约束，不是文风偏好。
- **批次 5**（StoryDefaults 结构对齐）：上游扁平 12 字段 ↔ 本仓三层嵌套。
  采用**「配置面向上游、内部保留嵌套」+ `normalizeStory()` 双向翻译**的折中——
  全量扁平化要改 15 个文件、约 78 处读取点，风险与收益不成比例。
  - `world` 是唯一类型冲突的键（上游字符串 / 本仓对象）→ union + **默认必须是对象**
    （union 无默认值会给 undefined，把 78 处 `story.world.setting` 打挂）
  - `isShellStory` 必须**先归一**：只填上游扁平字段的 story 否则被误判成空壳、
    静默回退到全局/预设（用户表现「配了没用」）
  - `storyForBot` 是全局唯一归一化点，78 处读取点不必各自兼容两种形状
  - 顺带补上两个**上游有、本仓原先没有**的能力：`perspectives[]`（多条独立
    价值观，**保持独立条目不合并**）与 `supplementaryFacts[]`（作为初始长期
    事实注入）
- **批次 8**（承诺机制收敛，事故的**结构性根治**）：此前批次 0 只是「收紧判据」

标记 → 生成器天然跳过；**测试读同一份来源**（原先两边各写一份，正是漂移的温床）。
并加了两条不变量：① 每条登记必须命中真实 schema 路径——否则第 3 阶段改键名时
会**静默解除隐藏**、假开关重新冒出来；② 命中即标记、前缀登记整段生效、未登记不受影响。

**第 3 阶段：改名兼容层已就位（`story` → `storyDefaults` 的第一步）**

新增 `lib/config-compat.js`：`normalizeConfigAliases(config)` 让**新旧两种写法在
所有读取点等价**——只有新名就填旧名、只有旧名就填新名、两个都有则**新名赢**并把
旧名对齐（不留两个不一致的副本）。

**做在配置入口**而不是去改几十处读取点：下游代码看到的永远是「两个名字都填好」的配置，
于是改名可以一步步做，而**用户 profile 里已有的 `story:` 不会失效**。设置路由的
GET 也走同一份归一化（面板读配置同样要认新名）。

9 项测试，重点不在「函数会不会算」，而在**两种写法会不会得到同一个结果**：
只写旧名 / 只写新名 / 冲突 / 都没写（不凭空造键）/ 不改入参 / 幂等 / 坏输入不抛。

**集成验证（已做）**：`phase23-e2e` 新增一条，走设置路由验证只写新名 / 只写旧名
两种情况下两个名字都被填上。

**验证过程中发现一个真实缺陷——它把下一步从「可选」变成了「必需」**：

- 只写**旧名**时，`story` 会被 schemastery **解析**（填默认值、补全形状）；
- 只写**新名**时，`storyDefaults` **不在 schema 里** → 是**透传原文**，不经解析。

归一化会把这份「未解析的原文」填给旧名，于是**下游拿到的形状不一致**。
结论：光把新名当「兼容别名透传」不够——**必须让 schema 认识新名**，
两个名字才会都经过解析、形状一致。原计划里「先兼容、再改名」的第二半因此是硬性的。

（这条测试里的断言已按事实写：旧名解析后、新名目前透传——**把缺陷钉在测试里**，
下一步改完 schema 后这条断言会提醒我把它翻过来。）

**兼容层因此补上了一层关键判断**：宿主在调用插件前已用 schema 解析过配置，而
schemastery 会给**没写的键**填默认值——于是「两个名字都存在」**不代表用户写了两个**。

实测踩到的坑（两个方向）：改名后配置里只有旧名时，新名被填成默认值，「新名赢」

所以 `normalizeConfigAliases` 现在接收 `defaults`（`Config({})`），判断改为：
**新名等于默认值、旧名不等于 → 认定用户写的是旧名**。

### 与上游配置面的对齐度（机器校验）

本目标的一句话是「面板不再与上游配置面漂移」。此前「还差多少」只存在于人的记忆

### 生成器数组字段类型错误（**已修**）

**现象**：生成式渲染对**数组字段**没有专门的转换分支——它落在文本框分支上：
显示时是 `String(array)`（纯量数组碰巧看起来还行），**写回时是字符串**。

**影响面**：`worldSeeder.blockedNames` **已经迁移**，正带着这个 bug：
用户编辑后保存，载荷里是 `"小鹿"` 而不是 `["小鹿"]`——**路径对、类型错**。
而覆盖度不变量**只看路径**，所以查不出来。

待迁移的段里还有 5 个数组字段会撞上同一个坑：
`storyDefaults.perspectives` / `supplementaryFacts`、`runtime.conversationFollowUpMinutes` /
`restWindows`（**对象数组**，需要 JSON 形态）、`presetSync.sections`、`im.allowedNativeFaces`。

**正确修法**（本轮已设计、未落地）：纯量数组用逗号分隔文本、对象数组用 JSON 文本域；
写回时按类型转回数组（JSON 解析失败则保留原文，交给 schema 去判）。
**并且必须配一条「先编辑、再保存、断言类型」的测试**——只断言播种结果是不够的：
不编辑就永远不会触发转换（这是本轮证伪时发现的）。

**修法（已落地）**：显示——纯量数组逗号分隔、**对象数组用 JSON 文本域**
（逗号分隔会把它们变成 `[object Object]`，`runtime.restWindows` 正是对象数组）；
写回——纯量数组按逗号切、对象数组按 JSON 解析（失败则保留原文交给 schema）。

**测试**：改值走的是「**先编辑该字段、再保存、断言类型是数组**」——
只断言播种结果是不够的（第一版就是这样，证伪时没红）。并已**先证伪**：
临时撤掉转换分支后两条断言如期变红。

**修的时候踩过一次（过程记录，值得记住）**：我的锚点
`} else if (field.control === 'number') {` 在文件里**出现两次**（`onChange` 的赋值链
与显示链各一个），插入落到了**前一个**——显示代码被塞进 `onChange`，把逻辑弄坏，
`blockedNames` 整个从载荷里消失、连带 3 条测试变红。已 `git checkout` 回到绿状态。

**教训**：锚点不唯一时插入会落到错误分支，而**症状离原因很远**（改的是显示，坏的是保存）。
下一轮修的时候把锚点做成唯一（带上前一行），并在插入后先核对插入点。

### 剩下两块大的：`im` / `runtime`（迁移前分析）

跨群投递**里，还混着「高级选项」折叠区；而 schema 的 `im` 是一个整段。
整段替换会把这些 UX 分组**全部打散**——那是重排，不是迁移。

**能力已就位（本轮）**：`autoFieldsFor('im', 'im.chunking')` 可按嵌套路径只渲染那一组；

——它是**先证伪过**的：登记 `im.chunking` 而不渲染，断言如期报出该路径下的 10 个字段缺失。

**因此需要一个能力：按子路径渲染**，例如 `autoFieldsFor('im', 'im.chunking')`
只画 `im.chunking` 的那 11 个字段，让每个手写块内嵌**自己那一组**。

**它连带要求改一处不变量**：现在的「内嵌段字段都必须被渲染」是按**整段**校验的，
部分内嵌时会把「没内嵌的那些字段」误报为缺失。所以清单要从「段 key」升级为
「**路径**」（段 key 或嵌套路径），不变量按路径解析出应渲染的字段。

**迁移顺序建议**（从独立度高的子组开始）：
`im.chunking`（11，自带一组控件）→ `im.forwardLimits` → `im.crossConversation` →
`im.interactive` → `im.proactive` → `im.group` → 最后才是 `im` 顶层 31 个与 `runtime`。

### 一条硬性约束：**登记内嵌与渲染必须同时到位**（本轮实测）

`EMBEDDED_PATHS` 一旦登记某项（如 `im.chunking`），`seedAutoDraft` 就会把**它所属的整个段**
（`im`）按「描述符默认值打底 + 配置叠加」播种进 `autoDraft`，保存时再合并进载荷。

后果：**如果那些字段其实还没有交给生成式渲染，播种出来的默认值会盖掉手写控件的值**
——用户的编辑静默失效。本轮实测到两处症状：

- 面板里改了「打字速度」（期望 20）→ 载荷里仍是默认 12；
- client-input：发消息间隔填 0 → 载荷里仍是 120。

两处都不是「字段没画出来」那么轻，而是**值被覆盖**。

**约束已解除（本轮）**：`seedAutoDraft` 改为**按登记路径的粒度**播种——
登记 `im.forwardLimits` 时只播种该路径的子树，不再把整个 `im` 种子化。
段内**部分迁移**因此可行，这是大段能一个个子组迁过来的前提。

**改动前实测的两处症状**（现已消失）：打字速度改 20 存成 12、发消息间隔填 0 存成 120
——都是「手写值被播种出的默认值盖掉」。

**所以迁移顺序是刚性的：摘手写控件、`autoFieldsFor` 调用、清单登记——三件事必须在同一次改动里完成**，
不能像改键名那样「先兼容、后切换」。

**这也解释了那条盲区断言为什么值得**：它表面上在查「字段有没有被画出来」，
实际上拦住的是「**登记了却没渲染 ⇒ 载荷被默认值覆盖**」这条更严重的通路。

**本轮没迁成（过程记录）**：摘除脚本三次失败——控件数自检写错（8 写成 9）、
按行区间摘除时**括号失衡**（`node --check` 立刻报出）。已 `git checkout` 回绿。
下次改为**逐块摘除**（复用 `presetSync` 那次跑通的「自动探测缩进」helper），
而不是一次摘一大段区间。

### 两件与「怎么看测试结果」有关的事

**① 面板夹具卫生已变成不变量**（连踩四次的坑，现在有护栏了）

面板的生成式段靠 `/panel-schema` 描述符才渲染，而**每个测试夹具都自带一个 fetch 假实现**
——没补描述符的夹具里，生成式段**根本不出现**。

症状很难认：不是「字段画错了」，而是「**整段不在那儿**」，于是按标签查找返回 null、
报错停在 `.props` 上。我为此在 `crossConversation` 与 `willingness` 上各绕了一轮。

现在有一条不变量**钉住断言了生成式段的那 4 个夹具**；其它面板夹具（只查载荷/样式/扫码流程）
暂时不需要，但**一旦开始断言生成式段就必须补上**。

**② `test:loadbearing` 会**故意**打印 FAIL 行——别被吓到**

它打印 7 行 FAIL（承诺兜底 3 条 + dsh-im 服务 4 条，含重复），但那**不是失败**：
那是**负控夹具**——故意关掉某个能力（如 `DISABLED=true`），断言「应有 N 条用例变红」，
以此证明那些测试**确实有区分力**。输出自己写着「关掉兜底后 3 条用例变红，退出码非 0」。

**所以它的信号是退出码**（必须 0），不是「有没有 FAIL 字样」。
我第一次见到时按字面理解、以为有 7 处失败——记在这里，免得下次再被同一串惊到。
