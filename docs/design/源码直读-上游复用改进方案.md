### 2.2 值得复用的具体条目

#### 【A-1】`md-to-plain.js` —— Markdown → QQ 纯文本（59 行，零依赖）

导出 `mdToPlain(md)` 与 `splitForQQ(text, max=4000)`。

**为什么本地需要**：本地 `lib/im.js` 只做**分条**（按句末标点 / 宽度），
`grep markdown|\*\*|\`\`\`` 于 `lib/*.js` **零命中**——即本地**没有任何 Markdown 剥离**。
`lib/render.js:105` 的 `storyRules` 明确要求模型"该有旁白、动作、环境就写"，
模型输出 `**强调**`、`` `code` ``、列表符很可能原样发到 QQ。

`splitForQQ` 还含一段**代理对保护**（把切点从 emoji 中间前移），
与本地 `lib/im.js:111` 的 `safeSliceIndex` 思路一致但实现不同，可互为参考。

**落点**：新增 `lib/vendor/md-to-plain.js`；在 `deliverToIm` 的文本出口处调用 `mdToPlain`。
**注意**：本地已有分条器（`splitImText`），**不要**同时引入 `splitForQQ` 以免两套切分打架——
只取 `mdToPlain`。

#### 【A-2】`safe-fetch.js` —— SSRF 防护（283 行，仅 2 处配置耦合）

**必须先说清楚一件事**：本地**当前没有**这个缺口。

实测 `grep "\bfetch\(|https\.request|http\.request"` 于 `lib/*.js` 与 `lib/qq-im/*.js`：
命中的**全部**是 `lib/client.js` 里浏览器侧的**同源** UI 调用
（`fetch('/api/hds-interlude/...')`）。`lib/qq-im/inbound.js` 只处理**文本**
（`renderInboundText`，L160），`lib/qq-im/outbound.js` 只 import `splitImText`。
`lib/index.js:69` 的 `inject` 也不含任何网络能力——联网归 DSH 宿主（如 `web_fetch` 工具）。

**所以 A-2 不是"补一个现有漏洞"，而是"为将来接图片/链接预留"。**
若短期不接图片下载，**本项可降级或延后**，不应作为最高优先级。

若确实要做（例如将来支持入站图片或由模型提供的 URL），该模块的质量是够的，依据如下：

| 能力 | 证据 |
|---|---|
| 私网判定覆盖广 | `safe-fetch.js:63-99`：含 `10/127/0`、`169.254`、`172.16-31`、`192.168`、**`100.64-127` CGNAT**(L75)、`198.18-19`(L76)、`192.0.0`(L77)、`>=224`(L78) |
| IPv6 内嵌 IPv4 递归解析 | `safe-fetch.js:66-67` 先 `parseEmbeddedIpv4(h)` 再递归；6to4 在 L89-94 单独还原 |
| DNS 全结果校验 | `safe-fetch.js:128-132` 遍历 `addresses`，任一私网即抛 |
| **DNS rebinding 结构性消除** | `requestOnce` 用 `hostname: ip`(L201) 发请求，同时保留 `host: url.host`(L206) 与 https 的 `servername`(L211) |
| 重定向逐跳重校验 | `safeFetch` L236-243：每跳重新 `validateFetchUrl(next)`，上限 `MAX_REDIRECTS=5`(L231) |
| 按字节限读 | `readBounded` L171 `total += chunk.length`（字节）；L174-176 注释记录了"字符数 vs 字节数"单位不一致的历史 bug |

**唯一需要的改写**：2 处 `getConfig()`
（`safe-fetch.js:252` 与 `:280`，均读 `security?.allowPrivateImageHosts`）
改为参数注入。

#### 【A-3】`util.js` 的 `createSendChain` —— 7 行串行队列（零依赖）

`util.js:147-155`：

```js
export function createSendChain() {
  let chain = Promise.resolve();
  return function enqueue(task) {
    const next = chain.then(task, task);        // 失败也继续链
    chain = next.then(() => undefined, () => undefined);
    return next;
  };
}
```

这是本方案里**性价比最高的一条**——配套见 §4.1（本地 P1）。

#### 【A-4】`model-vision-docs.js` —— 模型图片能力字典（403 行，零依赖）

`PROVIDER_DOCS` + `MODEL_DOCS` 两级判定，模型 ID 归一支持**斜杠前后双键匹配**
（`modelKeys()`，L23-31：`deepseek-ai/xxx` ≡ `xxx`），每条带 `note` 注明来源 URL。

**本地对应需求**：本地 `lib/qq-im/outbound.js` 只发文本，暂无图片能力判断需求；
**若将来接图片**，此表可直接作为只读参考。**当前优先级低。**

配套的 `vision-scan.js:50` `detectModelVision`（用 1×1 PNG 探测）也同理——**待接入图片时再取**。

#### 【A-5】档位前置判定 —— **架构借鉴，不宜直接搬代码**

上游 A 省 token 的机制在 `orchestrator.js:228-262`，源码注释（L228-235）写得很直白：

> 关键顺序：判定必须发生在 drainUnread() 之前。……
> 未命中时：标记已读、不创建会话、不调模型 —— **这才是省 token 的关键**

流程：`peekUnread`（只看不取，L240）→ `#predictTier`（L247）→
若 `shouldRespond === false` 则 `markAllRead`（L253）+ 让等待会话干净消失（L255）+ **return**。

**本地适配性评估**：本地是**单用户 DSH 会话**模型，没有"群聊里多条消息竞相触发"的场景，
`peekUnread`/`markAllRead` 的双语义在本地无对等物。**"预判不消费未读"这个巧思对本地不适用。**

**但其中一条原则可移植**：`resolveContextTier`（`prompt.js:344-378`）体现的
**"先判断值不值得调模型，再决定是否花上下文"**。本地已有的对应物是
`lib/index.js:2063` 起的 `STALE_INTENT_MS` 过期检查（过久不投递）与
`scheduleAdvance` 的间隔控制——**已具备同类思想**。
建议**不新增**档位机制，只作为设计参考记录。

## 四、复用映射

### 4.1 【P0】写路径串行化 + 不再静默吞错

| 项 | 内容 |
|---|---|
| 上游来源 | `A/src/util.js:147-155` `createSendChain`（主）；`B/src/service.ts:509/5384/5434`（同一模式，可参考重试策略） |
| 本地落点 | `lib/state.js:124` `saveState` |
| 复用方式 | **注入**：把 `createSendChain` 的实现搬进本地，按 key 建链 |
| 理由 | 见下方证据链 |

**本地证据（问题真实存在）**：

`lib/state.js:123-137` 原文：

```js
/** 原子落盘；失败静默（意图丢失不应打断对话）。 */
export function saveState(key, state) {
  try {
    ...
    fs.writeFileSync(tmp, JSON.stringify(state), 'utf8')
    fs.renameSync(tmp, file)
  } catch {
    /* 持久化是尽力而为的 */
  }
}
```

**这不是"可能有问题"，而是三重事实叠加**：

1. **静默**：`catch {}` 无任何日志（`lib/state.js:134-136`）。
2. **调用点极多**：`Select-String "saveState\("` 于 `lib/**/*.js` → **37 处命中**
   （`lib/index.js` **36 处调用** + `lib/state.js:124` 的 1 处定义）。
3. **确实存在并发写入**：`lib/index.js:2571` `await Promise.all(jobs)` 对**多个会话并行**跑
   `processSession`（L2569 push job），而 `inFlight`（L2556）只挡**同一 key 的扫描入口**，
   不覆盖工具处理器路径。

**改法**：`createSendChain` 7 行照搬 + 每 key 一条链；`catch` 改为
`console.warn('[hds-interlude] 状态落盘失败', key, error)` + 一个失败计数器。
**不要**引入上游的 7 次退避重试（本地是同步 fs，重试语义不同）。

**(待补充：需由用户确认)** —— 失败后是否需要向上暴露（例如状态卡片上显示"落盘异常"计数），
以及是否需要在 `/interlude status` 中呈现。本地 `lib/render.js` 已有 `renderStatus`，接入位置需用户定夺。

  **每个会话只注入一次**（L1052 置位，且 `grep canonInjected` 显示**无任何重置点**）。

- 每回合注入的是 `renderInterludeBlock`（L1069），它**本来就是可变内容**，
  且本地已经做过一轮"说一次就够"的裁剪（`render.js:248-252` 明确决定不放 `imBlockLine`）。

**结论**：本地**没有** B 那种"系统提示每 15 轮切一次变体"的问题。
`storyRules(deliverable)`（`render.js:105-121`）虽有 if/else 两个分支（L111 `if (deliverable)` /
L117 `else`），但因外层 `canonInjected` 门控，**同一会话内只会走一次**——
既不是每轮变化，也就不是缓存问题。

**因此 P3 的准确表述是**：本项**无当前收益**，仅作为**回归防线**——
若将来把 `renderRules`/`storyRules` 改成每轮注入，应当采用 B 的"恒定文本 + 标志行"写法。
**建议记录为设计约束，不安排工时。**

### 8.2 前提修正一：P1（overlay 证据门控）**前提不成立 → 改为补接线**


核验 `upsertOverlay` 的实际调用情况后发现：

- `Select-String lib/**/*.js "upsertOverlay"` **只有 2 处命中**：`lib/state.js:423` 的定义，
  与 `lib/index.js:33` 的 **import**；
- **没有任何调用点** —— 该函数是**死代码**；
- 唯一会改动 `state.overlay` 的是 `clearOverlay`（`/interlude overlay clear`）；
- `interlude_memory` 工具（`lib/index.js:1160`）的 `action` 只接受 `add` / `close`，
  **没有 overlay 写入入口**。

**结论**：overlay 与 `state.continuity` 是同一类问题 —— **被读取、被渲染，但没有写入路径**。
因此原 P1「给证据门控加判据」**前提不成立**：一个从不被写入的字段，加门控没有意义。

**正确的问题是"要不要给它一个写入路径"**。经确认后按「接上」处理，实际做了**两端**：

**① 写入端**（`lib/index.js`）：`interlude_memory` 新增 `action: 'overlay'`，
并复用 `upsertOverlay` **已有的** `layer` 枚举（`character` / `perspective` / `relationship` / `world`）
—— 没有新造字段名，参数与 `upsertOverlay` 的签名一一对应。

**② 读回端**（`lib/render.js`）：把 overlay 注入 `<幕间>` 块。
只做写入端是没用的 —— 函数有调用点了，但模型仍然看不到，等于换一种形式的死代码。

口径对齐上游 `narrator.ts:1508`：

> *Stable overlay is the accumulated present condition after repeated evidence and
> **takes precedence when it clearly conflicts with an old baseline**.*

即 overlay 是「反复证据累积出的当下」，与最初设定冲突时**以它为准**。
本插件在注入行的措辞里如实表达了这个优先级。

**一处必须同时改的联动**：`renderInterludeBlock` 开头有个 `substance` 前置闸
（`!alwaysReportTime && !gapNotice && !substance` 时直接 `return ''`）。
若只加注入行、不把 overlay 计入 `substance`，那么「**只有 overlay、没有其它事实**」的会话
会永远拿到空串 —— 写入路径接了也白接。已一并加入，并有专门的用例钉住这一格
（`test/overlay.test.mjs` 的「【关键】只有 overlay、没有任何其它事实时，仍然注入」），
且做过承重验证：去掉那一行子句，该用例立即变红。


### 8.3 前提修正二：P2 的真实收益**比预想的小，但修掉了一个真实 bug**

原判断「本地无任何 Markdown 处理」**不准确**。实际上 `lib/im.js` 的 `cleanImText`
（经 `splitImText` 在投递路径上生效）**已有**一套剥离规则：

```
lib/im.js:32  MD_BLOCK_PREFIX = /^\s{0,3}(?:#{1,6}\s+|[-*+]\s+|\d{1,9}[.)]\s+|>\s+)/
lib/im.js:35  MD_INLINE_MARK  = /(\*\*|__|~~|`)/
lib/im.js:29  ASTERISK_ACTION = /\*[^*\n]{0,200}\*/g
```

我最初的 grep 用了字面量 `**`，没命中这些**正则变量名**，因而误判。

**实测两者覆盖面**（同一输入分别过两条路径）：

| 输入 | 旧路径（`splitImText`） | 新路径（先 `mdToPlain`） |
|---|---|---|
| `**粗体**` | 粗体 ✅ | 粗体 ✅ |
| `## 标题` | 标题 ✅ | 标题 ✅ |
| `` `code` `` | code ✅ | code ✅ |
| `~~删除~~` | 删除 ✅ | 删除 ✅ |
| `- 列表项` | 列表项 | `• 列表项` |
| **`[链接](https://x.com)`** | **`""`（整段消失）** | `链接 (https://x.com)` ✅ |

**真实收益 = 修掉一个既有 bug**：`lib/im.js:26` 的

```
INLINE_NARRATION = /[（(【\[][^（(【\[）)】\]]{0,200}[）)】\]]/g
```

把 `[...]` 当作**旁白括号**处理，于是 Markdown 链接的方括号部分被整段删除 ——
用户看到的是「你看这个  写得挺清楚」，链接与链接文字**一起消失**。
先过 `mdToPlain` 会把链接转成 `说明文档 (https://x.com)`，方括号不再出现，该 bug 被绕开。

这条已在 `test/verify-md-strip-loadbearing.mjs` 中用**对照组**钉住
（先断言旧路径确实吞掉、再断言新路径保留）。

### 8.4 P3：`safe-fetch.js` 已移植，但**仍是"备用件"**

移植落在 `lib/net/safe-fetch.js`，保留了上游的全部防护逻辑：

| 能力 | 本地落点 |
|---|---|
| 私网判定（含 CGNAT `100.64/10`、保留段） | `isPrivateIp` |
| **内嵌 IPv4 递归判定**（防 v6 绕过） | `parseEmbeddedIpv4` / `ipv4FromLast32` |
| DNS 全结果校验 | `resolveSafeHost` |
| **IP 固定**（消除 DNS rebinding） | `requestOnce`：`hostname: ip` + 保留 `host`/`servername` |
| 重定向逐跳重校验 | `safeFetch` / `safeFetchBinary` |
| 按字节限读 | `readBounded` |

**唯一的改写**：上游 2 处 `getConfig()`（读 `security.allowPrivateImageHosts`）
改为**参数注入** `{ allowPrivate }`。这带来两个好处：符合本插件"无全局可变配置单例"的现状；
且这些函数成为**纯函数**，可离线测试。

**它当前没有调用点**，这一点必须写在明处（模块头注释里也写了）：
实测本插件**没有任何出站 HTTP**（详见 §2.2 A-2）。所以这不是补一个现存漏洞，
而是**为接入图片/链接能力预留的闸门**。

之所以"提前放进来"而不是等真要用时再写：等到那时，安全闸门会和业务改动绑在同一次上线里，
而且一个从没运行过的防护代码，与没有防护在心理上是等价的。
现在已有 13 项用例覆盖它（含 CGNAT、v6 内嵌 IPv4 绕过、公网不误判），**且不依赖网络**。

**(待补充：需由用户确认)** —— 将来真接入图片下载时，
`allowPrivate` 应对应哪个配置字段（以及是否要像上游那样默认 `false`）。本轮没有新建配置项。

**本轮的两个教训**（值得写下来）：

1. **grep 字面量会漏掉正则变量名**。P2 的误判与 `safe-fetch` 的过度乐观都源于此。
   核实"有没有某能力"时，应同时搜**用法**与**定义**（变量名、常量名），

2. **接线要接两端，还要核对闸门**。overlay 这类"有读无写"的字段，只补写入端仍等于死代码
   （模型看不到）；而补了注入端还可能被上游的前置闸（`substance`）挡掉。
   补一个字段的读写路径时，要顺着调用链把**闸门**一并核对。
