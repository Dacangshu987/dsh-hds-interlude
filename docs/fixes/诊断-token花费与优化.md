# Token 花费诊断：钱花在哪，怎么省

> 数据来源：`session-58be9b68`（QQ · hi）393 个事件、38 轮、40 次模型调用，
> 从会话日志里逐条还原（`lib/*.js` 同目录的分析脚本，结论可复算）。

## 先看总账

| 指标 | 数值 |
| --- | --- |
| 会话跨度 | 9/12 21:34 → 9/14 01:25（约 28 小时） |
| 轮数 / 模型调用 | 38 轮 / 40 次 |
| 上下文规模 | 4,797 → **17,237** tokens（×3.6） |
| 累计上下文 | **419,494** tokens |
| 累计新输入 / 缓存读 / 输出 | 127,638 / 284,288 / 7,568 |

上下文从 4.8k 涨到 17.2k，**每次请求都要把这一整块重发一遍**。
这就是「越聊越贵」的机械原因——不是单次变贵，是每一次都更贵。

## 三个真正的开销大头

### ① 低产出调用：65% 的钱花在「输出不到 30 token」的调用上

40 次调用里有 **22 次输出不足 30 token**，而这些调用累计吃了
**272,699 / 419,494 = 65%** 的上下文。

它们是什么？是「到点提醒」「自动续写」「你就回个 emmm」这类**一句话就够**的回合。
每一次都要把 15k+ 的上下文完整读一遍，只为了吐 10 个 token。

> 典型：turn 34 输出 6 token，上下文 16,425；turn 30 输出 8 token，上下文 15,862。

**这不是 bug，是长会话的固有成本**：一句话的回复和一篇长文的回复，读的成本一样。
要降它，只能降「读的东西有多少」——见下面的办法。

### ② 工具 schema：每次请求固定 2,825 token

`request/header` 里带了 **16 个工具**，schema 合计 9,886 字符 ≈ 2,825 token，
**每一次请求都重发**：

```
40 次 × 2,825 ≈ 113,000 token（占累计上下文 27%）
```

拆开看：

| 来源 | 字符 | ≈token |
| --- | --- | --- |
| `hds-interlude` 六个工具 | 2,708 | 774 |
| 其它十个（搜索/技能/侧栏/文件…） | 7,178 | 2,051 |

这是个**陪聊场景**（QQ 里聊日常），`advanced_search`、
`platform_search`、`create_skill`、`find_dsh_plugin`、`sidebar_open` 这些
一次都没用过，但每一轮都在付钱。

### ③ 幕间块：每回合注入一次，其中大量是无信息量的行

40 次注入，平均 **123 字**。实测内容分布：

| 内容 | 出现次数 |
| --- | --- |
| 「当前经由聊天软件发送：你的话会被拆成最多 4 条…」 | 40 / 40 |
| 「距上一条用户消息已过…」 | 39 / 40 |
| 「距你上次开口已过…」 | 39 / 40 |
| **真正有内容的（到期待办 / 连续性 / 气氛 / 日程）** | **0 / 40** |

也就是说：**40 次注入没有一次带来新信息**，全是时间戳和一条永远不变的发送约束。
其中 17 次写着「距上一条用户消息已过 **不到 1 分钟**」——用户刚说完话，
模型当然知道「刚刚」，这行等于没说。

这些东西一旦进入历史，就**从那一刻起被后续每一次请求重发**。
按「第 N 次注入要重发 (40−N) 次」累计，幕间块占了约 **20%** 的累计上下文。

## 已经改掉的（本次提交）

### 幕间块瘦身（`lib/render.js`）

| 改动 | 理由 |
| --- | --- |
| 间隔行只在**真的超过 `gapNoticeMinutes`** 时才写 | 「不到 1 分钟」没有信息量，白占位 |
| 「距你上次开口」门槛另取 max(阈值, 1 分钟) | 刚说完话的那几轮不必重复念叨 |
| 把「一次最多分 4 条、每条约 40 字」从幕间块**移到首轮规则段** | 它是**发送方式**的约束，不是这一回合的事实；说一次就够（原来说了 40 次） |

实测：幕间块 **123 → 62 字/次**。

```
单次注入省 ≈ 1,968 token（40 次）
考虑「进入历史后被反复重发」的累计节省 ≈ 40,344 token
→ 约占累计上下文的 9.6%
```

回归测试：`test/plugin.test.mjs` 新增 2 条——
「刚说完话不念叨间隔」+「隔了 5 小时照常注入（有信息量就不能省）」。

### 说明：`imBlockLine()` 现在还被 `export`

它仍然导出（有测试与外部引用），但 `renderInterludeBlock` 不再调用它。
内容已经并入 `imRules()`，在首轮规则段里出现一次。

## 还没动、但更值钱的三个办法

按「省得多 / 风险低」排序：

### 1. 关掉 `alwaysReportTime`（立刻，改一个键）

线上 `~/.dsh/settings.yaml` 里是 `alwaysReportTime: true`——**每回合都注入时间**。
这是那 40/40 次注入成行的直接开关。

```yaml
hds-interlude:
  alwaysReportTime: false      # 只在「隔得久」或有实质内容时才注入
```

`gapNoticeMinutes: 30` 会保证「隔了半小时以上」照常说时间。改完**无需重启**（配置热生效）。

代价：模型在「刚说完话马上又来一句」时不知道确切时刻。但那正是它不需要知道的时刻。

### 2. 裁剪工具集（省最多，要动 profile）

16 个工具里，陪聊用不到的至少 6 个（`advanced_search` 646 字符、
`platform_search` 313、`create_skill` 386、`find_dsh_plugin` 394、
`sidebar_open` 289、`ask_user_question` 1,079——后者在 IM 场景根本点不了）。

按每个 schema 的字符数算，砍掉这些大约省 **1,300 token/次**，
即约 **52,000 token**（占 12%）。

做法：给这个 QQ 会话用的 Agent Preset 单独裁剪工具清单
（`~/.dsh/.agent-presets/preset-hds-mtydnayg-xitbpo/agent.cordis.yml` 里加
disable 条目），让「江柚」这个角色会话只保留聊天真正用得上的工具。
**这是收益最大的一项，但需要按你的实际用法决定砍哪些。**

### 3. 开压缩 / 定期 `/compact`（治本，但要确认机制）

DSH 有 `compaction/summary` 与 `compaction/prune` 事件，但这个会话 **393 个事件里一次都没触发**。

原因很清楚：`request/context` 显示 `contextWindow: 1000000`（100 万），
而当前上下文只有 **17,237（1.72%）**。压缩阈值是**相对窗口大小**的，
窗口开到 100 万，就永远等不到自动压缩。

两条路：
- 换一个上下文窗口更小的模型（比如 `hy3-x` 的 192k），让压缩阈值落到实际会用到的量级；
- 或者按需手动 `/compact`（DSH 内置命令，dsh-im 侧 `/compact` 也有）。

> 注意：压缩会把早期对话换成摘要，**人物细节会丢**。
> 对「陪聊角色」这种靠细节吃饭的场景，这是有损的——
> 所以我把它排在最后，而不是推荐首选。

---

## 一句话总结

**最贵的不是插件，是「每轮都重发整个上下文」这个机制 × 越滚越大的上下文。**

- 立刻能做、零风险：`alwaysReportTime: false`（这次已把注入本身的废行删掉，两者叠加）；
- 收益最大：按实际用法裁掉用不到的工具 schema；
- 治本但有损：换小窗口模型让它自动压缩，或定期 `/compact`。
